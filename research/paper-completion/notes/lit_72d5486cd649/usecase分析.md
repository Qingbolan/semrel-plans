# 具体用例

**BIRD Dev 第 985 题的修正**（Figure 5，PDF p.7）：

- 原问题："在参加法国大奖赛的车手中，谁第 3 圈用时最慢？" 外部知识："最慢时间指 Max(time)"。
- 原金标准 SQL：连接 lapTimes 与 races，过滤 name='French Grand Prix' 且 lap=3，`ORDER BY T1.time DESC LIMIT 1`，输出 driverId。
- 发现的问题：(1) time 是文本列，按字典序排序会排错（E2）；(2) 输出车手姓名还是 ID 不明确（E4）；(3) 有多场同名"法国大奖赛"，问题可指任一场或全部合并（E4）。
- 修正：问题改写为"在历年所有法国大奖赛中……请给出车手 ID"；SQL 改为把 "分:秒.毫秒" 文本解析成毫秒数后排序；并向 drivers 与 lapTimes 插入一条时间为 "11:00.365" 的测试记录，使按文本排序的错误 SQL 不再碰巧得出正确答案。

**SAR-Agent 诊断示例：BIRD Mini-Dev 第 416 题**（附录 A.1，Figures 12–13，PDF p.15）：问题问"无 power 的卡牌中法语版占多少百分比"。SAR-Agent 先查出无 power 卡 31,053 张，再查连接 foreign_data 后膨胀到 128,569 行，再查出有法语翻译的无 power 卡 14,892 张，从而判断原 SQL 的分母按"卡×语言"计数，得到 12.97% 而正确值约 47.96%，并给出用 COUNT(DISTINCT uuid) 的修正查询。

**对排名的影响**：CHESS 在原子集排第 7（EX 62%），修正后升至 81% 并列第 1；其 12 个"仅修正金标准 SQL 后由错转对"的例子中有 5 个是标注者在 COUNT 里漏了 DISTINCT（§5.4，PDF p.9）。

阅读者分析：这些例子说明错误往往需要执行探查查询才能暴露（行数膨胀、文本排序），单看 SQL 文本难以发现；这也是作者让审核智能体可执行查询的理由。
