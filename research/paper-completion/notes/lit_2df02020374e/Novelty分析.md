# 贡献与评价

| 贡献 | 原文要点 |
|---|---|
| 多源证据准备 | 规则代码：用 JavaSymbolSolver 构建符号引用树，自底向上分层摘要；文档：分块抽取规则，SBERT 嵌入、UMAP 降维、GMM 聚类后汇总为规范规则说明；问答：从网站问答按标签与 LLM 过滤 |
| 结构-语义检索 | 结构嵌入 = 查询模板嵌入 + 匹配规则的 one-hot；语义嵌入借检索到的规则说明匹配问答解释；两者合并建索引 |
| 分步 LLM 改写 | 问答打分 → recipe 过滤排序 → 规则引擎改写 → 基于代价与 recipe 完成度的反思 |
| 部署 | 华为 GaussDB：慢 SQL（如超过 1 分钟）触发；若优于原改写，以 DSL 缓存查询模式并通过插件生效 |

阅读者分析：把 LLM 限定为“规则选择器”是该文最有用的设计，避免了 LLM 直接生成 SQL 的等价性问题。但改写能力受限于 Calcite 已有规则；证据库中 67 条规则说明需要专家校验，构建成本未量化。反思依赖优化器代价估计，代价不准时可能误判。

依据：[arXiv:2412.01661v2](https://arxiv.org/pdf/2412.01661v2)，§3–§6、Figure 3，PDF pp.3–9。
