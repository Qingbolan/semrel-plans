# 出发点

作者认为 NL2BI（自然语言到 BI 查询）是 NL2SQL 在生产中最受关注的场景，让产品、运营等非专家也能做数据分析（§1，p.1）。直接套用现有 NL2SQL 方法会遇到三个挑战（§1，pp.2–3）：

**C1 交互模式受限**：Spider、BIRD 都是单轮（SRD），而真实用户会多轮追问（MRD）。例如先问"近七天短视频播放量"，再问"周同比呢？""播放时长呢？"。LLM 首先需要判断一句话是否依赖前文（Fig.1，p.2）。

**C2 列多且歧义**：BI 表经 ETL 合并成宽表，常以视图形式存在。原文引用 Microsoft 的例子：一个财务数仓有 632 张表、4000 多列，以及 200 个视图、7400 多列。依赖 LLM 做 schema linking 会超出 token 限制，截断列又会使准确率骤降。同一指标还有多种叫法，如 "uv" 可指用户访问或独立访客数（p.3）。

**C3 现有流程不足**：BI SQL 常含复杂语义、同环比和计算关系；GPT-4 无法做 SFT，只能靠更长的提示，而提示越长效果越差，成本也高（原文称 GPT-4-32K 约为 GPT-3.5-turbo-instruct 的 60 倍；DIN-SQL 每条 SQL 约 $0.5）（pp.3、6）。

三个挑战都来自百度 BI 生产环境的经验，原文未给出定量分布（如 MRD 占比、歧义列比例）（阅读者分析）
