# 出发点

原文以多模态表上的问题为例（Fig.1，PDF p.2）：“Matt Damon 主演且 IMDb 评分高于 8.5 的电影平均票房”，主演需从海报图像中抽取。直接把整张表塞进提示会超出上下文窗口；用语义算子分解成逐批执行的原子任务则可行。

作者认为现有两条路线各有缺陷：在 SQL 引擎中加 AI 算子（ThalamusDB、CAESURA）与现有优化器兼容性差；从零构建的语义分析系统（Lotus、Palimpzest、DocETL 等）虽有系统级优化，但经典代价估计在选择率依赖 LLM 推理时失效，且质量成为一等优化目标（§1，PDF p.2）。

两个驱动问题（§1，PDF pp.2–3）：(1) 语义查询优化的首要目标是减少 LLM 调用，需要理解语义的改写，作者主张用 LLM 本身做逻辑优化，并认为即使优化开销远高于关系优化器，节省仍可超过开销；(2) 同一服务商提供多档模型（如 GPT-4.1/mini/nano），每个算子都可选择模型，因此存在“物理计划=模型选择”的优化空间；已有 Smart 只支持固定任务中单个算子。
