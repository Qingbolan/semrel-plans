# 出发点

原文把 LLM Text-to-SQL 分为两类（§1，p.1）：
- 训练类（预训练/微调）：需要大量标注与算力，且每当出现更强的新 LLM 就要重新训练，成本高、易出错。
- 零样本类（如 DAIL-SQL、C3）：无需标注和训练，但难以把预训练知识迁移到“自然语言 + 数据库 schema → SQL”这一具体映射上，处理复杂 schema 关系、构造复杂 SQL 以及保持鲁棒性都有困难。

作者的思路是把 SQL 生成拆成逐步构造的小子任务，每一步提供上下文引导，再用测试时搜索（MCTS）在巨大的组合空间中寻找正确路径（§1–2，pp.1–3）。作者还引用前人对 BIRD dev 的错误分析：约 20% 错误来自过滤列/值选错（CHESS-SQL），约 19% 来自函数错误（CHASE-SQL），以此作为加入相应动作的动机（§4.1，p.5）。

阅读者分析：动机是“用推理时计算替代微调”，代价是每题大量 LLM 调用与 SQL 执行，而这部分成本原文没有量化。

依据：[arXiv:2502.17248v2（ICML 2025，PMLR 267），21 页](https://arxiv.org/abs/2502.17248)。
