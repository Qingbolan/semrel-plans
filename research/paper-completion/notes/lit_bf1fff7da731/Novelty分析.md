# 贡献与评价

| 组件 | 做法 | 位置 |
|---|---|---|
| NLR2 | 在改写提示后加“描述你使用的改写规则”，并要求不写表名列名；有效改写对应的规则存入库，记录查询特征和观测加速 | §4.1，PDF p.5 |
| 主导规则识别 | 用每条 NLR2 单独生成改写，只用 `EXPLAIN` 比较计划代价或计划嵌入（bert-base-uncased，L2 距离），把观测加速归给最接近的那条规则 | §4.1，PDF p.6 |
| 规则分组 | 用多选提示让 LLM 判断新规则是否与已有规则等价，避免重复调用 | §4.1、Figure 5，PDF p.6 |
| 规则检索 | LLM 总结执行计划中的主要瓶颈，按嵌入检索 top-k 相似历史查询，再用 LLM 多选确认，取其最有效规则 | §4.2，PDF p.7 |
| 改写修正 | 语义修正：LLM 概括两条查询并构造反例；语法修正：把 `EXPLAIN` 报错交给 LLM | §4.3、Figure 6，PDF p.7 |

阅读者分析：与 LITHE（6 条固定手写规则）、LLM-R2/R-Bot（在 Calcite 规则内选择和排序）不同，GenRewrite 的规则库可以随负载增长，这是主要新意。代价是正确性依赖外部验证与人工检查：§6 说明 SQLSolver 只能验证 18.9% 的 TPC-DS 改写，评测中报告的改写都经过人工检查（PDF pp.12–13）。

Table 5 将发现的 7 类改写模式与已有文献比较，其中 2 类已有完全相同的结构化改写记录（PDF p.11）。主导规则识别假设一次改写的收益主要来自单条规则，作者承认这是简化（§4.1，PDF p.6）。

依据：§4–6、Table 5，PDF pp.5–7、11–13。
