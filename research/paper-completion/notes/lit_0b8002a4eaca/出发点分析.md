# 出发点

查询改写要求改写后的 SQL 可执行、与原查询等价，并且更快；改写本身的开销也应被节省的执行时间抵消（§1）。现有规则式方法分两条路线：发现新规则（WeTune、QueryBooster）需要复杂的规则验证或用户写专门的规则语法；选择已有规则（Learned Rewrite）依赖蒙特卡洛树搜索和学习的代价模型，计算量大，且代价估计不准会直接影响效果（§1、§2.3.1）。

另一方面，让 LLM 直接生成改写后的 SQL 会产生幻觉：语法或引用错误导致无法执行，或结果与原查询不等价。作者举例说专门针对 text-to-SQL 微调的 Granite-20b-code 在 BIRD 上只有 67.86% 的生成查询可执行（§2.3.2）。微调还只能用于开源模型，且换数据集需重新调优。

因此作者选择折中：让 LLM 只做“选规则”，由数据库改写平台执行规则，以保留 LLM 的泛化能力同时规避幻觉（§1）。

依据：[PVLDB 18(1) 53–65](https://www.vldb.org/pvldb/vol18/p53-yuan.pdf)，§1、§2.3，PDF pp.1–3。
