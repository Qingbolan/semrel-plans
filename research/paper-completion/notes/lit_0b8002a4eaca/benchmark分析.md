# 评测与边界

**基线**：Learned Rewrite（LR，MCTS + 学习代价模型）；LLM only（LLM 直接输出改写 SQL，不可执行或不等价时回退为原查询）（§6.1.4）。**指标**：查询执行时间（均值、中位数、75/95 分位）和改写延迟（§6.1.6）。

**实验 1（执行效率，Table 2，GPT-3.5，平均执行时间，秒）**：

| 方法 | TPC-H | IMDB | DSB |
|---|---|---|---|
| 原查询 | 70.90 | 6.99 | 60.55 |
| LR | 39.40 | 6.20 | 59.21 |
| LLM only | 70.67 | 6.96 | 61.60 |
| LLM-R2 | 37.23 | 3.91 | 24.11 |

**实验 2（改写数量，Table 3）**：LLM-R2 改写 323/302/341 条，其中改进 305/292/222 条；LR 为 258/203/456 与 192/197/193。

**实验 3（含改写延迟的总时间，Table 4）**：LLM-R2 每条查询改写延迟比 LR 多 1.82/1.86/1.51 秒，但总时间仍最低（TPC-H 40.63、IMDB 6.81、DSB 27.40）。每条查询 API 成本低于 0.001 美元，选择模型训练时间 3,305–6,571 秒（Table 5）。

**实验 4（消融，Tables 8–10）**：学习的选择器优于零样本、随机、树编辑距离和 SentTrans 选择；3-shot 反而变差（均值 54.08）；在提示中加入执行计划或基数树会大幅减少改写建议。

**原文承认的边界**：改写延迟高于纯数据库方法（§7）；提示调整敏感且无明显规律（§6.5.3）；推理时换用其他 LLM 会降低效果（§6.5.2）。

**口径差异**：§6.2 正文说 LLM only 在 TPC-H 的 129 次改写中有 119 次出错，但 Table 3 记为 197 次改写、68 次改进，两处口径不一致（阅读者分析）。Table 6 的 TPC-H 100G 使用 3,000 秒上限，与 §6.1.6 的 300 秒不同；Table 6 中 LR 在 10G 的 75 分位为 37.21，Table 2 为 32.21（阅读者分析）。

依据：[PVLDB 18(1) 53–65](https://www.vldb.org/pvldb/vol18/p53-yuan.pdf)，§6、Tables 2–10，PDF pp.8–12。
