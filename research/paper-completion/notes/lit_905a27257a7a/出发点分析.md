# 出发点

**原文陈述。** 多智能体工作流（如 Planner/Coder/Tester）中，各 agent 调用是独立的 LLM 请求，但共享系统提示、工具/agent 描述和上游累积历史，理想情况下工作流级 KV-Cache 复用命中率可超过 90%，实际受 GPU 显存所限（§1，p.1）。推理引擎默认的 LRU 依赖时间局部性，而工作流中缓存常在工具调用或 agent 切换期间长时间闲置后才被复用，LRU 会过早驱逐（§1，p.1）。

KVFlow 把 Belady 最优驱逐思想搬到多智能体场景，但假设存在预先定义的静态 agent 步骤图；真实工作流是动态的，例如 Tester 打回重写、Retriever 按中间结果派生子查询，未来调用顺序无法事先知道（§1，p.2）。

作者给出两个相互冲突的难点：（i）LLM 随机解码使 agent 调用轨迹难以预测；（ii）预测错误代价被放大——一次缺失可能需要重新 prefill 整个工作流累积的数万 token（§1，p.2）。因此核心问题是设计一个“对预测器质量鲁棒、且能从不完美预测中持续获益”的 KV-Cache 管理框架。

**阅读者分析：** 出发点属于 LLM serving 系统层，而不是语义查询/数据处理层；它把“工作流结构”当作缓存替换策略的输入，和数据库中基于查询计划的 buffer 管理思路相近，但论文本身未作这一类比。
