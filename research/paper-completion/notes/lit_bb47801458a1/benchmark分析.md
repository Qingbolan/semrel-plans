# 评测与边界

基线：Lotus（Pandas）、Palimpzest（MinTime 策略）、FlockMTL（DuckDB UDF）。为减少网络波动，全部使用本地 vLLM；Q1–Q5 用 Gemma-3 4B，Q6–Q20 用 Gemma-3 12B，温度 0；4×RTX 5090（§7.1–7.2，p.8）。

指标：分类类查询 Acc/Pre/Rec/F1；Q15 多标签用 subset Acc、micro/macro F1、Jaccard；Q16–Q20 先评过滤再评下游（关键词、分类、聚合文本的词重叠）；效率为延迟、LLM 调用数、输入/输出 token、成本（¢）。

主要结果：
- 延迟（Fig.4）：Sema 在 20 条查询上均最低；复杂查询 Q6–Q20 最高 3–6× 加速；摘要/引言给出相对 Lotus 2–4×、相对 Palimpzest 2–10×。作者将其主要归因于向量化、流水线并行与异步执行。
- 质量（Table 3、Fig.5）：Sema、Lotus、Palimpzest 互有高低；例如 Q1 F1 为 0.9967/0.9970/0.9723。FlockMTL 普遍较差，且不支持 Q1、Q5、Q19、Q20（正文；表注只列 Q1、Q5、Q20）；Palimpzest 不支持 Q20（无 SemAgg）。
- 执行优化（§7.3，Fig.6）：远程 API 下批处理和融合都降低延迟；本地 vLLM 下二者可能增加延迟；批处理一致降低质量；融合在 Q13/Q14/Q16 提升质量、Q8 下降。
- 表达式优化（Table 4）：Q3 加谓词推导后 LLM 调用 856→492(+2)，延迟 410.66s→135.11s；Q14 加推导后精度由 0.6134 降到 0.3787，原文未讨论该下降。
- AQE（§7.5）：延迟优先如 Q6 29.64s，成本优先如 Q6 2.21¢；规划时间为毫秒级（Table 6）。

边界：基准由作者自建且仅 20 条；Q6–Q20 真值为 Gemma-3 27B 输出；只用 Gemma-3 系列做主实验；作者承认提示差异会导致质量波动（§7.2）。阅读者分析：加速比较混杂了引擎执行模型差异与语义优化效果，主表并未逐项消融二者。
