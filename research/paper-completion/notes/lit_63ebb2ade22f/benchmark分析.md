# 评测与边界

**基线**（§6.1，p.7）：Guidance v0.1.8（llama.cpp 后端）、vLLM v0.2.5（默认 API 服务器；作者注明新版 vLLM 已部分集成 RadixAttention，故用旧版）、LMQL v0.7.3（HF Transformers 后端）；多模态用模型作者的 HF 原始实现。

**指标**：吞吐（programs/s）、延迟、缓存命中率（缓存命中的提示 token 数 / 提示 token 总数）。

**实验 1（开源模型端到端，Figs. 5–6，p.8）**：Llama-7B 单卡 A10G 上吞吐最高提升 6.4 倍、延迟最多降 3.7 倍；各基准缓存命中率 50%–99%，缓存感知调度平均达到最优命中率的 96%（Fig. 13）。多轮长输出几乎无加速，因为解码时间占主导。LMQL、Guidance 因速度慢或缺少功能未参加后五项。

**实验 2（大模型与多模态）**：Mixtral-8x7B（8×A10G）与 Llama-70B（4×A100）趋势相似（Fig. 7、Fig. 12）。

| 模型 | 原始实现 | SGLang |
|---|---|---|
| LLaVA-v1.5-7B（图像） | 0.18 image/s | 1.15 image/s |
| LLaVA-NeXT-34B（视频） | 0.02 frame/s | 0.10 frame/s |

（Table 2，p.9）

**实验 3（生产与 API）**：Chatbot Arena 一个月内 LLaVA-Next-34B 命中率 52.4%、Vicuna-33B 74.1%，后者首 token 延迟平均降 1.7 倍；GPT-3.5 抽取 3 个字段时推测执行使输入 token 成本约降为三分之一（§6.2，pp.8–9）。

**实验 4（消融，§6.3，p.9）**：去掉缓存、树结构、缓存感知调度、前端并行或前端提示均使性能下降（Fig. 8c）；无复用场景下 RadixAttention 管理开销 0.2 s / 74.3 s（<0.3%）；压缩 FSM 使 JSON 解码吞吐提高 1.6 倍，若不复用预处理则吞吐低 2.4 倍。

**边界**：结果以归一化图为主，未给出逐基准绝对值；只比较吞吐/延迟，不评估输出质量（作者默认关闭改变结果的优化）。阅读者分析：基线版本较旧（vLLM 0.2.5），加速倍数反映 2023–2024 年的对比条件。
