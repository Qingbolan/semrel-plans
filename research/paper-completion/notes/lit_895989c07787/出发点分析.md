# 出发点

**原文陈述（§1，p.1）。** 语义算子系统（Palimpzest、LOTUS、DocETL、Nirvana 等）普遍采用作者称为“解释式执行”的方式：运行时对每个数据项（单元格或单元格对）调用 LLM 解释算子谓词并直接给出结果。filter/map 的调用次数随行数线性增长，join 随候选对数增长，后者可能大得多；每次调用都带来延迟、费用和可能的限流开销，使大数据集上的语义执行极慢且昂贵。

受传统数据库把 SQL 编译成代码以加速执行的思路启发（引 HyPer/Neumann 2011），作者提出“编译式执行”：把 LLM 当作编译器而非解释器，给定算子、自然语言谓词、模式信息和可选的代表性样本，只调用一次 LLM 生成可复现算子意图的确定性代码，然后本地执行（§1，p.1）。

作者在先前的算子级实验（即同作者的 Vision 论文 arXiv:2607.13407，参考文献 [3]）中观察到效率提升大而质量损失小，于是提出系统问题：**如何在不替换现有语义算子系统原生执行引擎的前提下集成编译式执行？**（§1，p.1）

**阅读者分析：** 这是把“LLM 生成代码替代逐行 LLM 调用”上升为一个可插拔的物理算子选项和计划级路由问题，直接落在语义算子执行/优化层，与本项目关注的语义查询系统高度相关。
