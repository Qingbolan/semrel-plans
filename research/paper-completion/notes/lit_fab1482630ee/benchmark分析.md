# benchmark

**SWAN 主结果（Table 3A，80 条查询，3 次运行均值）**
| 系统 | EX % | Tuple-F1 % | Cell-F1 % | 平均时延 s | LLM 算子总成本 $ |
|---|---|---|---|---|---|
| LOTUS†（借助 oracle 信息合成程序） | 20.8 | 25.3 | 30.4 | 166 | 2.5969 |
| Palimpzest† | 12.5 | 17.1 | 18.5 | 585 | 47.5588 |
| Agentic Text2SQL（无 LLM 算子） | 19.2 | 22.8 | 28.0 | 142 | – |
| Agentic BlendSQL | 30.0 | 34.6 | 37.4 | 346 | 273.9520 |
| 智能体式查询执行（无经验池） | 32.1 | 36.5 | 39.9 | 235 | 3.1120 |
| + EnumGRPO | 35.4 | 38.1 | 41.4 | 153 | 0.8640 |

经验池让使用 LLM 算子的查询从 51 条降到 40 条，这些查询的平均 LLM 算子 token 从 52K 降到 18K（§5.1）。

**迁移（Table 3B–D、Table 4）**
- 跨数据库（只用其余三个库学到的经验）：EX 32.9%，每查询 0.010 美元。
- 跨主干（GPT-5.6）：EX 35.0%→35.4%，每查询 LLM 算子成本 0.106→0.036 美元，平均步数 14.6→12.5。
- SemBench Movie：Quality 0.713，BlendSQL† 为 0.712，LOTUS† 0.629，Palimpzest† 0.762（本方法略低）；成本 0.645 美元，对应 BlendSQL 15.049、LOTUS 86.430、Palimpzest 135.792。
- Spider/BIRD：EX 72.9→73.9、38.7→39.3，全程没有调用 LLM 数据算子，轨迹轮数缩短。

**规模（§5.5、Figure 3）**：BlendSQL 的时延和成本随规模增长（Superhero 0.25×→4×，成本 11.4→164.9 美元），智能体式执行基本持平。作者也指出，在更大规模下智能体趋向 SQL 优先，可能漏掉有用的语义证据。

**失败分析（§5.4）**：在一次 80 条运行中，52 条 EX 失败分为四类：执行/输出 4、行集构造 16、语义算子取值 17、SQL/规则取值 15。作者认为对中间结果做细粒度验证是关键挑战。

**局限**：原文没有独立的 Limitations 节。文中提到的有：学习成本 77.32 美元，在 1× 规模下约 1,677 条查询回本，低频工作负载不划算（§5.7）；部署时没有参考答案，难以定位错误（§5.4）；未来工作包括任务条件化的经验检索、持续学习和中间结果验证（§7）。阅读者分析：最佳 EX 只有 35.4%，绝对准确率仍低；LOTUS/Palimpzest 使用的是 oracle 辅助翻译的固定程序，并非其最佳的原生使用方式，跨系统差距应结合协议差异理解。
