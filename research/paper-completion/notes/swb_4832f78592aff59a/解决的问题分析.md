# 解决的问题

**任务单位**：一道问题。输入是一段背景（起始告警 `u_s` 及 k=2 个相关实体，作为上下文）和一个问题，问题指向另一告警 `u_e` 所连的一个实体 `v_e`；输出是提交的单个答案字符串，例如进程名、SID、IP（§3.2、Algorithm 1、Figure 3，pp.4–5）。

**环境**：每个事件（incident）一套 MySQL 数据库，含原始日志与告警表；智能体每步可执行一条 SQL（`execute[...]`）或提交答案（`submit[...]`），直到提交或达到最大步数。为防止上下文溢出，限制返回行数和字符长度（§3.3，p.5；E.2 给出 max_num_entry=15、max_char_len=100000，p.17）。

**不提供 schema**：提示中不给全量表结构（约 1,700 个列），智能体需自行 `SHOW TABLES` / `DESCRIBE` 探索（E.1，p.17）。

**奖励**：答案正确得 1；否则若开启步骤检查，从解法路径倒数第二步往前按 γ=0.4 衰减累加命中中间步骤的分数（Algorithm 2，p.5）。判定可用字符串匹配或 LLM 评审，主实验用 GPT-4o 作评审（§4.1，p.6）。

阅读者分析：这是"多表、无 schema 提示、多跳"的交互式 Text-to-SQL 调查任务，答案是表中某个实体值，而非开放式报告。

依据：arXiv:2507.14201v3，§3.2–3.3、Algorithms 1–2、附录 E.1–E.2，PDF pp.4–5、17。
