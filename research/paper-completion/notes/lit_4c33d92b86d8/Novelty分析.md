# novelty

论文声称四项贡献（§1 Contributions，p.2）：

| 贡献 | 内容 | 位置 |
|---|---|---|
| HRA | 把关系算子与 LLM UDF 统一的声明式代数，作为自动生成目标语言 | §2，pp.3–4 |
| 查询生成 | YAML 层次化语义数据模型（列类型、3 个样例值、描述、关系、领域规则）+ 过滤；ReAct 式问题分解（每个语义算子需给出理由）；对比式提示（精确 vs 含糊 UDF 名）与 5 个端到端示例 | §3，pp.4–6 |
| 代价优化 | 动态规划放置 LLM UDF（最坏 O(k·2^m)，m 为语义算子数），用 Z3 符号执行验证等价，超时/unknown 则回退原计划；无状态且确定的 UDF 由 LLM 改写成 SQL（如星座判断改成日期区间、湾区县改成 IN 列表） | §4，pp.6–7；§6.3.3，p.11 |
| 执行 | 去重后调用；语义连接 smart-batching：抽 3+3 个样本，由 LLM 根据连接难度、文本长度、基数决定批大小 b1,b2，调用次数降为 ⌈|K1|/b1⌉·⌈|K2|/b2⌉ | §5、Alg. 3，pp.7–8 |

**诚实评估（阅读者分析）**：
- 新意主要在系统集成与“自动生成 + 带等价保证的 UDF 放置”的组合。昂贵谓词放置、谓词下推、批处理 LLM 调用均有前作（论文自己在 §7 列出 BlendSQL 的规则式下推与延迟执行、Palimpzest/Abacus 的代价优化）。
- smart-batching 的批大小由 LLM 自评决定，没有给出准确率保证；“无准确率损失”只在 10 个连接查询上验证（§6.3.4）。
- UDF 改写依赖 LLM 判断“无状态且确定”，正确性没有形式化保证；论文未报告改写出错的比例。
- 论文内数字有口径差异：摘要写语义连接 LLM 调用平均减少 93%，贡献列表写 5–300×，§6.3.4 写“最高约 100×”；查询生成准确率 93.3%（§6.3.1）与端到端执行准确率 89.2%（Table 3）是不同指标。
