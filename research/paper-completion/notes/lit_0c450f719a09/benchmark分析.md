# 评测与边界

**基线**：LangChain 应用 + FastChat，后端为 vLLM 或 HuggingFace Transformers；按最短队列分配，所有请求视为独立且延迟敏感；每引擎设 token 容量阈值（Figure 10 显示超过 6144 后 TPOT 明显上升），超出后 FIFO 排队。另设“带共享”的 vLLM 静态前缀基线，以及吞吐型基线。

| 实验 | 主要结果（原文） |
|---|---|
| **实验 1（链式摘要，1×A100，13B）** | 相对 vLLM/HF 最高 1.38×/1.88×；固定输出长度时 1.2×/1.66×；有背景请求时 2.38×；25 个并发应用平均 1.68×，且无应用变慢 |
| **实验 2（map-reduce 摘要）** | 相对 vLLM 2.37×，来自 task group 用大批次 |
| **实验 3（Bing Copilot，7B）** | 相对无共享基线 1.8×–2.4×（批大小 8、16）；相对 vLLM 共享 1.1×–1.7×；批 32/64 时每输出 token 延迟 1.58×/1.84× |
| **实验 4（GPTs，4×A6000）** | 相对无共享基线可承受 12× 请求率；关闭亲和调度只剩 3×；新 kernel 相对 PagedAttention 2.4× |
| **实验 5（MetaGPT，13B）** | 相对延迟型基线最高 11.7×，相对吞吐型基线最高 2.45×（其中前缀共享贡献 2.35×）；16 文件时新 kernel 再快 1.2× |
| **实验 6（混合负载）** | 聊天归一化延迟比延迟型/吞吐型基线好 5.5×/1.23×；map-reduce 完成时间好 3.7×/1.05× |

**边界**：只测延迟、吞吐和显存，不测输出质量；网络延迟为注入模拟；Bing Copilot 只评估最后一个生成请求；更长上下文（32k 以上）不在范围内（§8.1）；动态控制流不支持（§6）。§8.2 正文称 Figure 11a/11b 分别对应 chunk size 和输出长度，而图注相反，引用具体曲线时需注意。（阅读者分析）

依据：[原文](https://www.usenix.org/system/files/osdi24-lin-chaofan.pdf)，§6、§8、Figures 10–19，PDF pp.8–14。
