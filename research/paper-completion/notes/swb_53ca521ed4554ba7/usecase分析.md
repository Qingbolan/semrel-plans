# 具体用例

**RTBF 失败的五类功能分组**（Figure 6，§5.3.1，PDF pp.10–12）：

| 功能 | 原文案例 |
|---|---|
| 验证 | 爱尔兰机构处罚 Groupon：注册时不需身份证，行使 RTBF 时却要求提供国民身份证 |
| 用户界面 | 瑞典机构谴责 Spotify：保留免费试用用户的信用卡信息虽有正当利益，但未向用户清楚解释拒绝删除的理由 |
| 策略决议 | 比利时机构认定 Google 误用例外，拒绝删除四个十余年前的 URL；某奥地利聚合服务以内容来自 LinkedIn 为由推卸删除义务而被罚款 |
| 应用软件 | Rebtel 在用户要求后仍继续发邮件；Høje-Taastrup 市使用无法按需删除的第三方处理者；Brico Prive 只停用账户而不删除数据 |
| 数据管理 | 丹麦机构处罚 Taxa：用客户电话号码作数据库主键，导致无法删除；英国机构处罚 Clearview AI：无法识别属于某人的全部照片 |

**分布结论**：UI 和策略类失败最常见，合计占全部失败的 80%。作者据此建议计算机社区优先投入 RTBF 的 UI/UX 和例外处理策略，其次才是应用与数据库改造（§5.3.2，PDF p.12）。

阅读者分析：Taxa"电话号码当主键"这类案例可直接转为数据库设计层面的检查项，例如在模式分析时标记以个人数据为主键的表；这是项目派生用途，原文未做此类自动化。
