# 出发点

**动机示例**（§1 Figure 1，p.1–2）：收入异常调查中，planner 把任务派给 searcher（取聚合数据）、analyzer（归因）、connector（关联产品事件与工单）和 editor（汇总假设）。这个 workflow 会反复起草相同的 SQL（如按 SKU 的周收入）和相同的 API 调用（抓取并解析新闻）。同一 workflow 还常被复制到不同市场、产品线或时间段批量运行，数十到数百个调查并发。

**现有系统各缺一块**（§1–2，Table 2，pp.2–3）：

| 类别 | 例子 | 缺什么 |
|---|---|---|
| 请求级服务引擎 | vLLM、SGLang | 请求彼此独立，看不到跨请求的逻辑重复（C1）；不管 CPU 工具（C2） |
| 通用数据平台 | Ray、Spark、Dask | 能执行 DAG，但把算子当黑盒，用不上 prefill/decode 与 KV cache（C3） |
| 应用编排器 | LangGraph、AgentScope | 有 agent 交互逻辑，但与服务运行时解耦，不能跨会话批处理 |

**三个挑战**（§2，p.3）：C1 结构感知——多个 agent 走相同子图，应合并而非逐个执行；C2 异构流水气泡——CPU 上的数据库/HTTP 未完成时 GPU 空等；C3 有状态算子——切换模型要重新加载权重，丢失热 KV cache 会增加推理延迟。

**并发规模**（Table 1，p.2）：多 agent 仿真项目已从 25 个 agent（Generative Agents）增长到 10,000 个（LMAgent），作者以此说明跨请求批处理的空间。

阅读者分析：收入调查只是引言中的动机示例；主评测的 6 个 workflow 是作者构造的 "synthetic yet representative" 负载（§6.1），不是企业生产查询日志。
