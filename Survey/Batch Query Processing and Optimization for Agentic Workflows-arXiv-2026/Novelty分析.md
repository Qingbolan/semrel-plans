# Novelty 分析

批量执行同一种 Agent 工作流时，每个请求都包含 LLM 推理与 SQL、HTTP 等工具操作。若各请求独立执行，共同提示词和相同工具调用不能充分共享，CPU 与 GPU 的依赖等待也会浪费资源。Halo 要解决的是：在逻辑工作流已经确定的条件下，如何优化整批工作的执行成本与完成时间。

## 作者贡献：用自己的话概括

1. **「工作负载表示」把整批 Agent 请求作为共同优化对象。** 联合表示 LLM 与工具依赖，暴露各自执行时看不见的公共计算和资源冲突。

2. **「成本优化」联合决定共享、算子放置和调度。** 将提示词/KV 复用及规范化工具调用共享纳入代价，减少跨请求重复工作和 CPU/GPU 等待。

3. **「执行系统与验证」让批处理适应不同阶段的计算与缓存状态。** 用流水执行和批量策略落实计划；v2 报告批量及在线场景最高分别 3.6×、2.6× 加速，不能套用其他版本的数字。

## Strong points（我们的判断）

1. 同时考虑模型和工具节点，更贴近包含数据库/API 的工作流（§3–5）。

2. 明确采用语义保持优化，收益不依赖降低目标答案质量（§6.8）。

3. 包含批大小敏感性和执行时间线，解释过度批处理为何产生阻塞（§6.6–6.7）。

## Weak points（我们的判断）

1. 固定逻辑 DAG 假设限制在线结构调整；需要执行中新建步骤的任务不能直接由现有方案覆盖（§6.8）。

2. 单机多 GPU 结果没有包含跨机缓存迁移及网络调度成本（§6.8）。

3. 批量加大后会拉长阶段执行并阻塞下游，吞吐收益不能无条件转换为单请求延迟收益（§6.6）。

来源位置：§3–5 系统与优化，§6 实验，§6.8 限制；[论文](https://arxiv.org/abs/2509.02121v2)。上述贡献归纳不主张未经核验的“首次”。
