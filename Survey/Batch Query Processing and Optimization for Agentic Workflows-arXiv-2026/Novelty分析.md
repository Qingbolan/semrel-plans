# 贡献与评价

**论文声称的贡献**（§1，p.2）：
1. 首个把 LLM 服务与查询优化结合、同时处理 GPU 上 LLM 算子和 CPU 工具算子的系统；
2. 依赖与资源感知的放置/调度优化器，以及求最优的 DP 求解器；
3. 支持跨 workflow 批处理、KV cache 共享/预取、计算–通信重叠的查询处理器；
4. batch 与在线两种模式下的延迟、吞吐提升，且不降低输出质量。

**阅读者评价**：
- 最直接的新能力是在一个批次内跨 workflow 合并完全相同的工具调用，并把 GPU 驻留状态与 CPU 准备代价放进同一个调度代价。消融显示合并工具调用是最大收益来源（去掉后 W6 慢 2.54 倍，Table 5）。
- 它只做物理层优化：逻辑计划固定，不改写提示或换模型。作者在 §7（p.12）明确把自己定位为 DocETL、Palimpzest、LOTUS 这类逻辑优化器之下的运行时，二者互补。
- “不降低输出质量”在摘要和 §1 中被声明，但论文没有给出逐查询的输出质量对比表；依据仅是语义等价的执行约束。
- 合并工具调用以“相同签名结果可共享”为前提。论文规定严格语义等价，但没有讨论有副作用、非确定性或依赖外部可变状态的 API；不能把它推广为“任意 HTTP 工具都可合并”。
- DP 最坏情况仍是指数级；“实际近线性”的说法只在单机 ≤3 GPU、6 个 workflow 上得到验证。

**论文承认的局限**（§6.8，p.11）：只支持单机多 GPU；假设固定的逻辑 DAG 与严格语义等价，不能做以精度换成本的改写，也不能在线改变 workflow 结构。另外主实验每个 workflow 最多 3 种模型，这是为了让需要预先部署 vLLM 后端的基线能运行（§6.1，p.8）。

依据：[arXiv 2509.02121v2](https://arxiv.org/abs/2509.02121v2)，§1、§6.5、§6.8、§7、Table 5，PDF pp.1–2、8–12。
