# 解决的问题

**输入**：一份 YAML 声明的 workflow（每个节点给出模型、system prompt、父节点、SQL 或 API 配置）、一批用户查询和设备配置（§3 Figure 3，p.4）。Parser 把它转成带类型的 GraphSpec，并把嵌在提示里的 SQL/API/本地函数拆成独立的 CPU 节点。

**输出**：ExecutionPlan，即每个 LLM 节点在哪个 epoch、放在哪个 GPU worker 上执行；Processor 在运行时按计划执行（§3–4）。

**优化目标**（§4，pp.4–5）：状态 S_e=(D_e, H_e)，D_e 为已完成的 LLM 节点集合，H_e 为各 GPU 的驻留模型与 KV cache 摘要。每个 epoch 选一批前沿节点 B_e 和到 GPU 的单射映射 φ_e，代价为 μ·max_w T_w + (1−μ)·Σ_w T_w + λ·g(A_e)，三项分别对应瓶颈 worker（makespan）、总负载和每个 epoch 的固定开销。

**代价模型**（§4.1，p.5）：T = T_prep + T_model + T_infer。T_prep 是上游 CPU 工具准备时间（SQL 用 DBMS 的 EXPLAIN 估计，HTTP/UDF 用按签名的移动平均）；T_model 在驻留模型不匹配时计重载代价；T_infer 用标定的 prefill/decode 吞吐曲线，命中共享前缀时扣减 prefill token。

**求解**：带备忘的 DP（Algorithm 1），只枚举拓扑前沿上的合法批次。最坏状态数 O(2^{N_V}·(N_m N_V)^M)，作者称实际可达状态主要随前沿宽度增长（§4，p.5）。CPU 线程不是显式决策变量；Processor 按到下一个 LLM 节点的 DAG 深度优先调度工具节点（§4、§5，pp.5–6）。

**运行时**（§5，pp.6–7）：事件驱动的 Coordinator 推进就绪队列；工具后端限并发并施加背压；对“类型+规范化参数”完全相同的待执行工具调用只执行一次再扇出结果（request coalescing）；同一 epoch 内复用 prepared statement；GPU 侧用引擎自带的 continuous batching，按波前推进而不设全层屏障；在不破坏即将用到的 GPU 状态的前提下机会式执行其他就绪任务。

**约束**：语义严格等价，不改写提示、不用代理模型；单机多 GPU（§3 Scope，p.4）。

阅读者分析：DP 的“最优”是相对离散化的 epoch 模型与估计代价而言，不等于在真实随机耗时下的全局最优；论文用 MILP 对照（§6.3）提供的是经验证据。

依据：[arXiv 2509.02121v2](https://arxiv.org/abs/2509.02121v2)，§3–5、Algorithm 1、Equations 1–2，PDF pp.3–7。
