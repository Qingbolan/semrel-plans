# 具体用例

**原文示例一：收入异常调查**（§1 Figure 1，pp.1–2）。多个并发调查中的 agent 会请求同一周、同一 SKU 的收入 SQL，或抓取同一篇新闻。Halo 发现重复提示并跨 agent 批处理摘要请求，对共享前缀复用 KV cache，并在依赖与资源约束下与 CPU 工具并发执行。

**原文示例二：W6 TPCH-Fanout**（Table 3、Figure 5，p.7）。9 个 LLM 节点、12 个工具节点，分两阶段把查询参数广播给多个 agent，每个 agent 执行由 TPC-H 模板实例化的分析 SQL，最后汇总指标。冗余 I/O 多，因此合并工具调用的收益最大：

| W6 上的现象 | 数值 | 位置 |
|---|---|---|
| 相对编排框架的 batch 加速（W5/W6） | 2.4–3.6× | §6.2，p.9 |
| 相对 OpWise | 1.6× | §6.2，p.9 |
| 去掉 request coalescing | 延迟 +154%（2.54×） | Table 5，§6.5，p.10 |
| 去掉机会式执行 | 延迟 +56% | Table 5，p.10 |

**合并的边界**（§5，pp.6–7）：只有“算子类型 + 规范化参数”完全相同的待执行调用才合并为一次物理执行；同一 SQL 模板但参数不同的调用只能共享 epoch 内的 prepared statement，不算同一查询。

阅读者分析：若在本项目中记录 Halo 风格的数据契约，应分开存放三类信息：环境数据（DB schema、索引、已装载数据）、输入（查询参数批与 workflow 定义）、执行配置（epoch 切分、模型驻留、worker 数）。后者不是用户查询的数据列。
