# 出发点

**应用需求**（§1，p.1）：医疗机构手里有数十万份疾病、药物和机构文档。一位症状为泡沫尿、钝性腰痛的病人需要先查出可能的疾病，再找到能治这些病、离家不远的公立医院。这需要跨文档的 join 与过滤，单个 QA 实例不足以测试系统。

**系统差异大、缺少统一评测**：各系统在查询接口（Python 或 SQL）、分块、逻辑优化、物理算子实现上差别很大，不清楚哪个系统适合哪种场景（§1）。各系统论文自己的评测规模也很小：
- ZenDB 只有 3 个数据集、221 篇文档、27 条查询，gold 不公开；
- Palimpzest 只有 1,000 封短邮件和 1 条查询；
- DocETL 有 5 个数据集，但每个只定义 1–2 个可抽取属性。

**四个设计目标**（§1，p.2）：
1. 数据量大（文档数多、单篇长）；
2. 数据集和查询多样（领域、模态、算子组合、选择率）；
3. 标签精确；
4. 易于评测现有系统。

**关键思路**：为每类文档预先定义关系 schema，并人工抽取全部属性值作为 gold，构成一个“关系数据库视图”。任何系统都可以用自己的接口执行查询，再与同一份关系 gold 比较，不要求各系统采用相同的执行计划（§1 Example 1）。

依据：[arXiv 2510.27119v1](https://arxiv.org/abs/2510.27119v1)，§1、Example 1，PDF pp.1–2。
