# 解决的问题

**系统剖析框架**（§2，Figure 1、Table 1，pp.2–5）：把 UDA 系统拆成四层，并逐层对比 7 个系统。

| 层 | 内容 | 各系统做法举例 |
|---|---|---|
| 查询接口 | SQL 类 / Python API | UQE、ZenDB、QUEST 用 SQL 类语言；DocETL、Evaporate、LOTUS、Palimpzest 用 Python |
| 逻辑优化 | 过滤重排、过滤下推、join 顺序 | Palimpzest/UQE 只看选择率；ZenDB 用 sel×平均 cost；QUEST 按每篇文档的 cost 排序，并把 join 转成 filter |
| 物理优化 | 模型选择、级联、算子分解、并行 | Palimpzest 做模型选择；LOTUS 做级联；DocETL 做算子分解 |
| 数据处理 | 分块、嵌入、多模态 | ZenDB 用语义层次树；QUEST 建文档级和块级两级索引 |

**Filter 的两种实现**：Palimpzest、QUEST、ZenDB 先抽取属性值再判断条件；LOTUS、DocETL、UQE 把条件放进提示，让 LLM 直接回答真假（§2.2）。

**基准构造流程**（§3，pp.5–7）：原始文档 → 统一 JSON（每个对象是一篇文档，字段为 text、image URL、metadata）→ 定义属性 schema → 人工标注并用 LLM 交叉校验 → 得到关系 gold → 用查询模板实例化查询。

**查询生成**（§3.4，p.7）：
- 每个数据集由博士生按真实场景设计 5 个模板，同时有 SQL 类和 Python 代码两种写法；
- 脚本随机采样 SELECT 属性、过滤属性与运算符（≤、=、≥ 等概率）、literal（用来调节选择率）、聚合函数，join 路径则预先定义；
- WHERE 中 1–5 个过滤条件的占比依次为 20%、30%、30%、10%、10%；
- 共 240 条查询，其中 220 条单表、20 条多表。

**指标**（§4.1，pp.7–8）：
- 准确率：返回元组与 gold 元组匹配后，计算每条查询的 P、R、F1，再取平均；
- 成本：每篇文档每条查询平均消耗的千 token 数；
- 延迟：每篇文档每条查询的平均秒数。

成本和延迟都不是美元或单条查询的总耗时。

**适配说明**：
- Evaporate 先抽出表，再执行 SQL；
- ZenDB 和 UQE 没有公开代码，由作者重新实现部分组件；
- 其他系统也做了修改，细节在附录。

阅读者分析：结果反映的是本基准适配后的配置，不等于各系统原生、不加修改时的排名。查询限定在预定义的 147 个属性上，可复现性强，但不覆盖任意开放式问题。
