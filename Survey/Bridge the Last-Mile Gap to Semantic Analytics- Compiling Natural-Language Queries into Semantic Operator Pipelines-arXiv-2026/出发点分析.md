# 出发点

**手工搭流水线的负担**（§1，pp.1–2）：语义算子系统提供 `sem_filter`、`sem_join`、`sem_agg` 等算子，但用户必须自己决定调用哪些算子、按什么顺序、写什么谓词、作用在哪个数据源上。这需要同时理解问题语义、数据结构和算子接口。

**隐含的桥接实体**（§1，p.2）：运行例子问“人口比 Boskovice 少、但比其他城市多的南摩拉维亚城市，其民俗节多久举办一次”。答案所在城市 Kyjov 从未出现在问题中，必须先在人口表上做排名推断才能找到，再用它连接到介绍该城市的 Wikipedia 文本。

**流水线随查询变化**：有的问题只需表过滤，有的需要跨模态 join 再聚合；同为“哪个 X 的 Y 最大”的问题，因数据源不同，流水线也不同。为每条查询手写流水线不可扩展，在运行时接收查询的自动化工作流中更不可能（§1，p.2）。

**后端 API 各异**：不同后端的执行模型、列引用语法和结果提取方式不同，一步把自然语言翻成代码会同时混淆数据定位、计算逻辑和接口语法（§1、§3.4）。

**与 Text-to-SQL 的区别**（§1，p.3）：Text-to-SQL 假设数据在关系库里并生成 SQL；NL2Pipe 面对表、文本、图片混合的数据上下文，生成的是谓词为自然语言的语义算子序列，能表达“把表行和文本段落按语义连接”这类 SQL 难以表达的操作。

依据：[arXiv 2606.04641v1](https://arxiv.org/abs/2606.04641v1)，§1、§3.2，pp.1–4。
