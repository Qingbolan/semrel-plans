# Workload分析

## 求证什么

长上下文模型能否从大量真实系统遥测定位故障；与把采样数据放进prompt相比，让Agent写代码分步取证是否更有效。作者提供挑战基准，不宣称已解决可靠生产诊断。

## 数据与任务

AIOps挑战三套系统：Bank 136、Telecom 51、Market 148，共335案例，68.5GB、5.23亿行指标/日志/调用链。原始1,753记录经筛系统、平衡、人工核验后保留；不是随机生产事故样本。NL查询由故障记录合成，要求组件、时间、原因的七种字段组合，提供候选值及故障数量。以人工核验标签评分：全部所需字段匹配为Correct，部分元素匹配另报Partial；起始时间允许一分钟误差（§2、§4）。

## 具体用例：在线商城故障定位

图3的案例问2022-03-20 09:00–09:30期间一次故障的组件与原因，gold为shippingservice-1及container read I/O load。**使用前：** 将每分钟采样的遥测和少量KPI装入约100K-token prompt，让模型直接判断。**使用后：** RCA-agent的Controller按指标→调用链→日志组织分析，Executor写Python筛查，观察结果后继续取证，避免仅靠原始上下文（§3）。

这是原文任务加两种执行方式的解释性对照；论文没有报告此单例两种方法的成功率或耗时。匹配的整体实证是Claude3.5在335案例上Balanced 3.88%、Oracle 5.37%、RCA-agent 11.34% Correct（表2），不能写成此故障从失败变成功。选该例是因为目标、时间窗和可核验答案明确，能说明数据处理到底服务什么判断。

## Baseline与边界

- Balanced Sampling：每分钟取首条，并从各指标文件分层随机抽KPI；运行三次取中位数。
- Oracle Sampling：工程师预选53个诊断KPI，原空间1,263个；含特权信息，是采样方法的理想化参照，非普通可部署对照。
- RCA-agent：Controller/Executor与状态化Python；六个长上下文模型用于采样，预算原因Agent只测三闭源及Llama3.1，不能当作六模型全矩阵。

Claude上的整体改善不能外推全部模型：Gemini1.5 Pro的RCA-agent Correct为2.69%，低于其Oracle的7.16%。未知故障数、缺失遥测案例、传播解释质量和跨案例复用并未在该设置中验证。
