# 解决的问题

**任务**（§II-A，p.2）：每个案例是一段 30 分钟的多模态遥测加一个自然语言查询，要求恢复根因的 ⟨时间, 组件, 原因⟩ 中的某个子集；一个窗口可能有多个故障。组件与原因必须来自各系统封闭的候选集。

**输入**：窗口内的指标、调用链、日志；查询；声明式适配器给出的文件格式、候选层级、部署拓扑和资源类型到原因的映射（§III-A、§III-D，pp.3–6）。

**两阶段方法**（§III，Figure 1，pp.3–5）：

| 阶段 | 步骤 | 作用 |
|---|---|---|
| 确定性证据抽取 | 形状感知检测 | 按全天分布把序列分为 dead、saturated、low-baseline、normal 四类，各用匹配的检测器 |
| | 多模态卡片构建 | 指标、调用链、日志各自检测，统一成（组件, 资源类型）证据卡，附粗粒度候选原因 |
| | 共部署汇总 | 按拓扑把同节点多个慢 pod 汇总为节点卡、同服务 pod 汇总为服务卡 |
| | 阈下兜底 | 没有卡片时给出最接近阈值的线索，保证输入不为空 |
| LLM 推理 | 只读工具（Table II） | `list_entries`、`get_component`、`get_kpi_series`、`get_golden_signal`、`get_call_graph`、日志摘要与采样、`submit_answer`；工具按模态是否存在而开放 |

答案的时间取自证据卡的起始时间，而不是由模型计算；最后按注入故障数对答案做调和（§III-C，p.5）。

**继承的假设**（§V-B，p.10）：封闭的候选组件与原因集、已知故障数、可用的拓扑信息。这降低了任务不确定性，不等同于开放类型的诊断。

**未覆盖**：跨记录探索共享的必要性、适用条件和净收益（阅读者分析）。

依据：[arXiv 2609.19825v1](https://arxiv.org/abs/2609.19825v1)，§II-A、§III、§V-B、Figure 1、Table II，pp.2–6、10。
