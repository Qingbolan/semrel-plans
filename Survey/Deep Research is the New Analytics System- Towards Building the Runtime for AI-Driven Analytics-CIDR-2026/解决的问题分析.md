# 解决的问题分析

来源：[原文](2509.02751v1.pdf)，§2–4、表 1–2。

- **输入**：自然语言分析目标，以及包含数据描述、迭代/索引访问方法和可选工具的 Context。
- **输出**：compute 生成指定结果；search 主要丰富 Context 的描述，记录搜索所得信息，再供后续计算使用。
- **核心困难**：任务可能需要选择性寻找正确文件，也可能需要遍历全部记录；Agent 的灵活计划不能保证完整、经济地执行，固定语义流水线也不适合所有证据查找任务。
- **实现**：用 CodeAgent 实现 search/compute，使其能迭代写代码和调用工具，并生成交给 Palimpzest 优化执行的语义程序。ContextManager 对物化 Context 的描述进行嵌入与缓存，为后续查询检索上下文。

## 实现与愿景的边界

Context、多种访问方式、Agent 执行和优化语义程序已有原型。Context 检索复用是实验性实现；拆分/合并 search 与 compute、运行时插入 search 等逻辑优化明确是未来工作。不能将这些方向描述成已验证的自适应优化器（§3）。

## 两个查询说明了什么

| 任务 | 主要结果 | 解释边界 |
| --- | --- | --- |
| 132 个文件中的身份盗用统计比值 | 原型平均误差 0.02%，手写语义程序 17%；成本 $1.17 对 $1.66，耗时 583s 对 215.2s | 更准确、成本较低，但更慢；手写程序的误差与额外输出错误比值有关 |
| 250 封邮件中的交易讨论筛选 | 原型与 CodeAgent+ 的 F1 均为 98.67%；原型成本 $0.87 对 $3.76，耗时 546.2s 对 1,999.9s | 优化降低同等检索质量下的开销；普通 CodeAgent 的 F1 为 50.53%，但更便宜、更快 |

各查询重复三次。邮件任务只评估返回邮件的 precision/recall/F1，未评估 sender、subject、summary 的抽取质量。表 2 的约 1.95× F1 收益来自 Enron 邮件任务；引言贡献列表将该数字关联到 Kramabench，与 §4/表 2 不一致，此处按实验表归属。

## 尚未回答

没有评估大规模数据上的稳定性、Context 复用收益或适用性判定，也没有研究多个记录的 Agent 探索如何共同调度。本文不能证明逐记录 Agent 普遍昂贵，更不能证明任意 Context 相似就可安全复用。
