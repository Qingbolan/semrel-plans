# Novelty 分析

## 问题定义与重要性

在异构文件集合上回答问题，既可能需要“找到少数正确证据”，也可能需要“完整检查所有相关记录”。作者观察到，语义算子程序容易对前一类任务做过多扫描或选错文件，而 Deep Research 容易对后一类任务只做关键词搜索和少量验证，遗漏结果。问题因此是：**如何让系统根据任务和中间观察选择数据访问方式，同时把需要完整执行的工作交给可优化的数据处理程序？** 这关系到系统能否同时避免无关处理和不完整答案，而不只是让 Agent 多几个工具。

## 作者贡献（用自己的话归纳为三条）

1. **「执行方式」把动态探索与优化后的批量处理接到同一查询过程中。** 查找统计文件需要边看边决定下一步，邮件筛选则需要完整检查；search/compute 让 Agent 在探索和代码执行中调用优化后的语义程序，使两类工作可以在同一分析任务中配合。
2. **「数据访问抽象」让数据集合同时支持查找与遍历。** 找一个统计值不应总是逐文件扫描，找全相关邮件也不能只依赖抽样搜索；Context 将数据描述、索引、迭代和工具一起交给 Agent，使它能按当前需求选择访问方式。
3. **「结果复用」让已完成的探索为后续查询提供上下文。** 重复查找和解析相同数据会重复支付推理成本；作者缓存并检索物化 Context，尝试复用之前找到的信息，但这一能力仍是初步实现，论文未单独验证收益。

来源：[原文](2509.02751v1.pdf)，§1–3。三条是对作者愿景及原型贡献的归纳，不表示其提出的全部优化已经完成。

## Strong points（我们的判断）

1. **问题由两个互补任务支撑。** 统计查找暴露固定逐文件处理的不足，邮件穷尽筛选暴露 Agent 漏检的问题，说明两种执行方式各自为什么必要，而不是笼统主张 Agent 更强（§1，图 1）。
2. **验证了“提供工具”与“优化程序执行”的区别。** 邮件任务中，CodeAgent+ 与原型 F1 相同，但原型成本降低 76.8%、耗时降低 72.7%，直接支持把可批量工作交给优化器的价值（§4，表 2）。
3. **把探索结果纳入可复用的数据对象。** Context 承接数据访问及搜索所得信息，使后续步骤和查询有机会利用已完成的工作；贡献在于明确复用对象，但其收益尚待验证（§2.2–2.4）。

## Weak points（我们的判断）

1. **实验尚不足以支持广泛适用性。** 只有两个查询、每个三次运行，邮件集仅 250 条且不评估抽取字段质量；无法据此判断复杂长链分析或大规模数据上的稳定表现（§4）。
2. **关键自适应决策仍依赖 Agent，而非已验证的优化策略。** 何时切换访问方式、拆分或合并操作、失败后补查证据，尚缺完整选择与代价评估；§3 的逻辑优化均为未来工作。
3. **Context 复用缺少有效性与收益证据。** 描述相似不保证证据口径、数据版本或覆盖范围一致；论文未给出充分的复用判定、更新维护和独立实验，尚不能确定何时复用既正确又划算（§2.4–3）。

## 对本项目的约束

“结合 Agent 探索与语义算子优化”以及“复用探索 Context”已是本文明确方向。本项目若聚焦逐记录探索，需要进一步说明哪些决策必须按记录产生、哪些工作可跨记录共享，以及共享为何不会损失必要证据；这些问题仍需具体工作负载验证。
