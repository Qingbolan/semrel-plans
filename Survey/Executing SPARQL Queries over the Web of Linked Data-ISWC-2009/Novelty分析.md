# 贡献与评价

**论文声称的贡献**（§1，p.2）：
1. 一种在 Linked Data Web 上执行 SPARQL 查询的方法：在执行中沿 RDF 链接发现数据；
2. 用迭代器流水线实现该方法的形式化描述（§3–4）；
3. 迭代器范式的扩展，避免等待 Web 数据造成整条流水线阻塞（§5）。

**机制要点**：

| 组件 | 内容 | 位置 |
|---|---|---|
| 流水线 BGP 匹配 | 每个三元组模式一个迭代器，Open/GetNext/Close；Succ 与 Ω 的形式化，Proposition 1 证明静态数据集上结果完整 | §3，pp.4–7 |
| EnsureRequirement | 求值前确保相关 URI 已解引用，必要时等待 | §4，Fig. 3，pp.7–8 |
| URI 预取 | URI 一出现在解中就异步发起解引用，不等后继迭代器需要 | §4，Fig. 4，pp.8–9 |
| 非阻塞迭代器 | 新增 Reject：数据未到时把输入解退回前驱，稍后再处理；GetNext 随机决定返回新解还是被拒绝过的解 | §5，Fig. 5，pp.9–11 |

**阅读者评价**：
- 优点：把“来源在执行中才出现”具体化为可执行规则（Requirement 1），并给出一个兼容同步流水线的非阻塞方案，不必改写成异步流水线（§5 p.10）。
- 优点：作者主动承认结果不完整、顺序影响完整度、跨查询共享数据集需要缓存失效处理（§2、§4、§8）。
- 局限：只覆盖 BGP；结果完整度没有任何量化评测；真实查询（Table 1）没有对照组，性能实验只在单台模拟服务器上做，规模 4,971–26,108 三元组（§6.2）。
- 与 SemRel 的关系（阅读者分析）：这是“执行中发现数据源”的早期数据库式实现，可作为运行时发现并非 LLM 系统独有能力的先例。

依据：[作者预印本](https://olafhartig.de/files/HartigEtAl_QueryTheWeb_ISWC09_Preprint.pdf)，§1–6、§8，pp.2–15。
