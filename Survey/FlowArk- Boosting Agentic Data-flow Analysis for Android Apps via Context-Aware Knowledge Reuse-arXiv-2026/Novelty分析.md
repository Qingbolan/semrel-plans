# Novelty 分析

安全分析需要从多个敏感输入出发，判断数据是否流向危险 API。不同 Agent 虽从不同输入开始，却会走到共同的回调、分发器和跨组件代码；彼此隔离的上下文使同一段代码被重复阅读和推理，增加整批分析的费用。

关键观察是：可以共享的部分往往直到工具返回文件、方法或字段后才显现；等 Agent 主动想起检索历史，重复分析可能已经发生。因此问题既包括保存什么，也包括何时把已有分析交给当前任务。

## 作者贡献：用自己的话概括

1. **「问题认识」指出批量数据流分析的重复理解成本。** 不同源点的分析会汇入共同代码，初始任务描述又不足以预先识别全部交集，使逐实例执行重复付费。

2. **「知识复用方法」把已完成分析变成可在运行时匹配的代码知识。** 按当前工具观察及时提供共同代码的解释，减少重分析，同时保留当前源点仍须验证的任务。

3. **「实证贡献」在真实 Android 应用中检验净成本收益。** 50 个应用、4,685 个任务的实验计入知识管理费用，报告总费用下降 26.83%；质量结论受抽样审计与相对召回口径限制。

## Strong points（我们的判断）

1. 复用对象和触发时机均由真实代码路径交汇解释，直接支持“执行后才发现共享机会”的动机（§II）。

2. 将管理成本计入总费用：603.49 美元降到 441.59 美元，避免只报告省下的推理费用（§V-B）。

3. 同时比较通用记忆、历史检索和模块消融，有助于识别收益来自何种复用设计（§V-D–E）。

## Weak points（我们的判断）

1. 质量审计基于抽样任务及各系统报告结果的并集，不能给出全部真实泄漏的绝对召回率；“质量相当”应保留这一口径（§V-A）。

2. 代码知识依赖当前快照；更新后需要版本锚点和失效处理，长期运行的净收益仍未验证（§VI）。

3. 没有报告墙钟延迟；费用下降不能直接推出更快完成整批任务，且本地 embedding 成本未完整货币化（§V、§VI）。
