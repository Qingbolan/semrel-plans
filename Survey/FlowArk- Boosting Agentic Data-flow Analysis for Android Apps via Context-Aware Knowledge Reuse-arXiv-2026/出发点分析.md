# 出发点

**场景**（§1，pp.1–2）：隐私合规审计、安全审查等 Android 分析中，分析师可能定义数百个不可信的 UI 输入源点，让 agent 判断每个源点的数据能否到达敏感 sink API。为控制任务复杂度和上下文长度，这些任务分给多个上下文隔离的 agent 实例。

**瓶颈**（§1，p.2）：现代 Android 应用把事件分发等常用逻辑封装成共享组件，从不同源点出发的数据流会汇入同一段共享代码。这类代码往往涉及回调、事件分发或组件间通信，需要跨文件多步确认，重复分析代价高。传统静态分析早就用摘要、缓存和增量更新来避免重复，但批量 agent 分析缺少跨实例的对应机制。

**通用记忆系统的两个不足**（§1，p.2）：
1. 提取不精确：完成的分析历史混杂冗长的工具调用日志和任务特定结论，Mem0 这类面向通用编码辅助的记忆可能保存低价值内容；
2. 复用时机不可靠：通用记忆依赖 agent 自己发起查询。复用机会在初始任务描述中看不出来，要等工具调用暴露出与先前分析重叠的文件、方法或字段后才出现；等 agent 想起检索，共享代码可能已被重新分析。

**核心思路**：把复用从“agent 主动检索记忆”改为“由运行时上下文触发、基于规则匹配”的知识注入（§1，p.2）。

依据：[arXiv 2607.11308v2](https://arxiv.org/abs/2607.11308)，§1、Figure 1，PDF pp.1–3。
