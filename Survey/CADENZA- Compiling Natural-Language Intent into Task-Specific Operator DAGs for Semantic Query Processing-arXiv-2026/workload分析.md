# Workload分析

## 求证什么

对同一个语义算子意图，拆出任务步骤并选专用模型、符号处理和LLM，是否比仅调整通用算子实现更能改善质量、时间及费用；同时检查优化开销、规模、意图特定计划与不同效用权重（§7、附录A–E）。

## 数据与任务

使用SemBench五场景、55条查询：Movie 10、Wildlife 10、MMQA 11、Cars 10、E-Commerce 14。表2规模分别为20,000影评；4,000图片和650音频；MMQA各表300行；99,929投诉、19,156车辆图片、871音频；5,000时尚商品。来源为既有真实内容数据集及其benchmark任务，不等于自然采样的业务查询流；Medical因许可问题未采用。

输入为绑定数据上的filter、map、join、分类和排名等意图，输出为相应关系结果。使用benchmark gold：检索F1、聚合相对误差、排名Spearman相关、分类/分组ARI，映射到[0,1]；另测秒数与美元费用。通常50个验证样本、20次BO；主实验关闭计划缓存，规划和执行并行度20（§7.1）。

## 最有说服力的具体用例：区分车辆图片中的两种损伤

Cars Q8要求识别图片里的轮胎穿孔与漆面刮痕。**使用前：** 被测基线以单个LLM oracle处理两类损伤，原文报告F1为0.08–0.35。**使用后：** CADENZA先用粗粒度图片分类筛候选，再仅让LLM核验正候选，F1为0.56（§7.2、图4(d)）。

这是原文逐查询结果，说明任务分解能同时改变处理范围与判别方式；不是所有损伤分类器都会失败，也不能把场景平均成本倍率附在此单例上。另一个直接例子是Cars Q3先按手动变速器字段筛选再看图片，但主要支持过滤下推，不能单凭它证明全新任务表示必需。

## Baseline与公平性

- LOTUS v1.1.4：GPT-4.1-mini oracle，nano/embedding proxies；作者为top-k增加拉取执行与取消调用。
- Palimpzest v1.1.1 + Abacus：MaxQualityAtFixedCost，10美元预算，GPT-4.1 judge；目标与CADENZA加权效用并非天然一致，附录D另对齐目标比较。
- ThalamusDB v0.1.15：近精确目标，误差设0并去token上限；不代表其近似模式下的最优表现。
- DocETL v0.2.6：质量导向，只评文本，关闭结果缓存，平均三次成功运行。
- Extended AFlow / DyFlow：补入专用模型节点与费用/延迟目标；这是作者扩展版，不是原版开箱结果。

主结果表3排除不支持或失败查询；图中部分E-Commerce超时项由小规模外推，质量来自小规模。跨查询平均倍率不能当成全覆盖保证；缓存摊销数据单列于表4。支持已绑定输入上的任务优化，未证明未知来源探索的必要性。
