# 解决的问题

**输入**：一个自然语言问题；用户提供的工具定义（描述与参数）；可选的 Planner 少样本示例（§4.1，p.5）。

**输出**：基于工具结果的最终答案。中间产物是任务 DAG：每个任务是一次工具调用，依赖前驱结果的参数写成占位变量（如 `$1`），执行时再替换为真实值（§3.1–3.2，p.4）。

**三个组件**（§3，Figure 2）：

| 组件 | 作用 |
|---|---|
| Function Calling Planner | 用 LLM 把问题分解成任务及依赖；可流式输出任务（§3.1、§4.2） |
| Task Fetching Unit | 贪心地把依赖已满足的任务发给执行器，并替换占位变量；不需要 LLM（§3.2） |
| Executor | 异步并发执行工具；工具可以是函数、搜索、API，也可以是另一个 LLM 智能体（§3.3） |

**动态重规划**（§3.4，p.5）：当执行图依赖事先未知的中间结果时，Executor 把结果送回 Planner 生成新一轮任务，循环直到得到答案。§5.3 的 24 点实验就靠这一机制，因此不能把本文概括为“只支持静态 DAG”。

**优化目标**：在不降低答案质量的前提下减少端到端延迟和 token 成本；准确率提升被视为附带收益（§1 p.2）。

阅读者分析：方法正确性依赖 Planner 写出的依赖是否完整。原文附录 B 显示 Planner 错连依赖的情况很少，但没有对“漏依赖导致错误并行”给出形式保证；工具若有副作用，能否重排也未讨论。

依据：§3–4，PDF pp.3–5；§5.3，p.8；附录 B，p.15。
