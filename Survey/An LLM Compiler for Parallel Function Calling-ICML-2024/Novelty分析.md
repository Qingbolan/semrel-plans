# Novelty 分析

用户要比较多个实体或组合多步工具结果。ReAct每次决定一个调用，独立查找也串行等待，长上下文还增加费用。论文观察到，很多工具依赖能整体表达；即使需要后续重规划，也可先并行完成当前已知的独立任务。

## 作者贡献（用自己的话概括）

1. **「执行表示」**将多次工具调用及依赖交给统一计划表达，让不相关的查找无需逐个等待（§3）。
2. **「运行时执行」**流式发出计划并在依赖就绪时调度，兼顾规划开销与工具并行；需要时可重规划（§4–5.3）。
3. **「实验贡献」**用独立调用、依赖调用与重规划任务检验答案质量、延迟和token成本，公开ParallelQA补充复杂依赖模式（§5、附录I）。

## Strong points（我们的判断）

1. 独立、依赖与动态重规划分别评测，避免用单一种并行模式概括全部任务（§5）。
2. 补充ReAct†提示修复重复调用与过早停止，使改进不只来自弱提示基线（表1、附录A）。
3. 流式消融及token/延迟分开报告，有助识别计划与执行的成本来源（表2、附录C）。

## Weak points（我们的判断）

1. ParallelQA只保留Wikipedia首段可回答的问题，刻意排除了困难检索；不能推广为开放环境发现能力（§5.2）。
2. 主要任务数量与依赖形态有限；同样工具可并行不代表复杂业务操作无副作用或可任意重排（§5，适用性判断）。
3. 动态实验用24点与附录WebShop说明能力，但没有证明所有开放式任务规划都稳定或不会漏依赖（§5.3、附录B/K）。
