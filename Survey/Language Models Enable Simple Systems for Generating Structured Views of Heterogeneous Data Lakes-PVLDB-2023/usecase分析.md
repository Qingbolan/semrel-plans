# 具体用例

**原文场景：FDA 医疗器械 510(k) 审查报告建表**（§2、§3.2–3.3，pp.3–7）。输入是一批 510(k) 上市前通知 PDF，目标是得到一张"器械"表，含 510(k) 编号、产品代码、分类等属性。

**使用 Evaporate 之前**：要么每份 PDF 都交给 LLM 读一遍（Direct），要么为这个领域专门写抽取器。

**Evaporate-Code+ 的流程**：

1. Schema 识别：LLM 只看少量样例文档，列出候选属性，再对并集重排序，得到如 "510(k) number" 等属性；
2. 函数生成：对每个属性，用关键词检索找到提到该属性的文档片段放进 prompt，换不同的上下文示例，生成多个 Python 抽取函数（Figure 4）；
3. 聚合：在样本上把函数输出与 LLM 抽取比对，过滤低质函数，剩余函数在全部文档上投票，用弱监督得出最终值。

**空值的歧义**（§3.3，p.7）：产品代码可能以小写 k 或大写 K 开头，某个函数只处理小写，于是在大写文档上返回空串。这与"文档本来就没有该属性"是两回事，因此不能把 null 一律当真实缺失；Algorithm 1 用 LLM 在样本上区分这两种情况。

**Direct 在 FDA 上的问题**（§4.4.1，p.11）：每篇平均漏掉 4.4 个金标准属性（27.5%），并多输出 9.7 个文档中没有明说的属性或值；"classification" 属性在 10 篇样本中有 4 种不同写法。

**效果**：FDA 上 Code+ 的 Pair F1 为 62.8，Direct 为 45.5；每万篇文档 token 从 145.6M 降到 1.9M（77 倍）（Table 3）。

依据：[arXiv 2304.09433v3](https://arxiv.org/abs/2304.09433v3)，§2–4、Figure 4、Table 3，pp.3–11。
