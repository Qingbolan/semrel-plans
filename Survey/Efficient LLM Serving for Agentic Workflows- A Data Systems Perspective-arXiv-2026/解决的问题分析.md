# 解决的问题

**输入**：一个用 Python DSL 声明的工作流模板（符号 DAG，算子为 LLM 调用、数据读取、格式化、Lambda 等），一批绑定到占位符的输入实例，以及可选的离线 profiling 统计（各 LLM 算子平均输入/输出 token 数）（§3、§6，pp.3–7）。

**输出**：与朴素执行逐字相同的结果，目标是最小化整批的端到端延迟（makespan）。

**范围假设**（§2 “Scope”，p.3）：语义保持，不用代理模型等近似；本地多 GPU 部署，不调用云 API；agent 只调用 LLM 和本地数据操作；所有 agent 使用同一个基础模型，仅以不同提示扮演角色。

**逻辑层**（§4，p.4）：
1. 算子剪枝：从输出节点反向遍历，删除不影响输出的算子（类似死代码消除）；
2. 公共子图消除（CSE）：按拓扑和输入标识哈希，合并结构相同且输入相同的子图；
3. 提示缓存替换：自底向上按“算子类型 + 已物化输入值”算签名，查全局缓存，命中则换成 CacheFetch 算子。只缓存确定性算子（非 LLM 算子与 greedy 采样的 LLM 算子），LRU 驱逐；不做语义近似匹配。

**物理层**（§5，pp.4–7）：
- TRT 同时表示静态 token 段、待其他算子输出填充的占位符，以及叶子（LLM 算子）之间的依赖边；
- 代价模型以“token step”为时间单位：prefill 只计与同 worker 上一个调用不共享的 token，decode 按 ½·len·(len+1) 累计，并加入“前驱完成后至少等待若干 token step”的延迟约束以鼓励穿插独立调用、增大批次；
- 目标是最小化总 token step，作者证明该问题 NP-hard（由并行机 makespan 归约）；
- 算法 1 在算子级 TRT 上做 DFS 式贪心（关键路径启发），输出每个 worker 的嵌套“软调度”，运行时可按就绪情况调整；复杂度 O(|V_int|·c_max³ + |E′|·d_max)，与批大小无关。

**执行层**（§5–6）：首次执行时预计算并固定静态前缀的 KV 缓存（改造 vLLM v0.16.0 支持 pinning），后续批次直接复用；内存紧张时仍按 vLLM 块级 LRU 驱逐，被驱逐的前缀下一批重算。

阅读者分析：profiling 统计是调度的前提（§6 “Job Profiling”），作者称开销小但未给出数字；实验中用不同查询集离线 profiling，因此端到端延迟不含这部分准备成本。

依据：[arXiv 2603.16104v1](https://arxiv.org/abs/2603.16104v1)，§2–6、算法 1、附录 A–B，PDF pp.3–7、14–18。
