# 具体用例

**Trading 工作流**（§7.2，Figure 6，p.9）：每支股票是一个查询，经过三个阶段。
1. 分析阶段（Parallel）：market、social media、news、fundamentals 四个分析师各自读取股价历史、社交帖子、新闻、公司财报并总结；
2. 研究阶段（Debate）：看多、看空两位研究员在经理主持下辩论分析结果；
3. 决策阶段（嵌套 MapRed）：分成 8 条链，每条由一种风格的交易员（如价值型、新闻型）给出初步决策，再经 3 个风控 agent 多轮辩论；最后基金经理汇总为投资建议。

**Helium 在其中的动作**（§7.6，Figure 13，p.13，以分析阶段子图为例）：
- 逻辑层：查全局提示缓存，发现 fundamentals 与 social media 分析师的输出已有缓存（输入跨天未变），用 CacheFetch 替换，剪掉两条分支；
- 物理层：先连续执行 market 分析师的 Op1、Op2，以复用它们共享的提示前缀；在等待依赖算子 Op3 时插入 news 分析师的独立算子 Op4、Op5，避免空等；Op3、Op6 在输入就绪后执行。

**调度为什么重要**（§5，Figure 4，p.5）：Agent 1 先回答问题（Op1），Agent 2 回答同一问题（Op2）并评审 Agent 1 的答案（Op3）。按 TRT 应排成 1→2→3，使 Op2、Op3 连续复用 Agent 2 的系统提示；在线算法可能排成 2→1→3，期间 Agent 2 的前缀 KV 可能被驱逐而需重算。

**案例中的度量**（§7.6，batch=16，关闭提示缓存以只看调度）：Helium 每批平均请求数是 LangGraph 的 1.18×，有效批 token 峰值高 1.41×；单请求中位延迟 28.3 s → 20.5 s，p95 51.7 s → 37.2 s。

阅读者分析：缓存有效性来自输入签名完全相同与已知依赖，不是对文本做语义合并；若公司资料每天变化，CacheFetch 不会命中，只剩前缀复用与调度收益。
