# Novelty 分析

多步骤 Agent 服务反复执行相似子任务，单个 LLM 请求级别的调度看不到未来依赖和整个工作流里的复用机会。因此即使底层推理很快，重复结果计算、重复前缀处理和依赖等待仍可能主导端到端时间。Helium 用完整工作流信息协调结果缓存与推理缓存，目标是保持语义的同时降低服务延迟。

## 作者贡献：用自己的话概括

1. **「系统视角」把 Agent 工作流当作可整体优化的查询计划。** 将 LLM 内部可共享计算暴露给上层，避免只优化孤立请求而忽略依赖链。

2. **「复用优化」主动识别可用结果与前缀缓存。** 已有确定性结果可替换对应子图；尚须执行的请求则共享 KV 状态，分别减少重复任务和重复预填充。

3. **「调度优化」在依赖与缓存局部性之间联合安排执行。** 通过模板前缀结构和成本信息组织请求，兼顾并行与复用，降低端到端工作流延迟。

## Strong points（我们的判断）

1. 区分结果复用和 KV 复用，便于明确收益到底来自哪里（缓存设计与优化章节）。

2. 案例展示跳过已缓存分支后如何重新调度剩余工作，解释完整工作流信息的实际价值（§7 案例）。

3. 明确列出动态控制流和外部 API 边界，给后续研究提供可核验的适用条件（§9）。

## Weak points（我们的判断）

1. 依赖执行结果的循环与动态展开仍需扩展控制流表达（§9）。

2. 结果复用受确定性和输入一致性约束，不能据此认为相似任务可安全共享完整答案（结果缓存章节）。

3. 外部工具耗时难预测，当前 best-effort 处理削弱复杂 API 环境中的全局调度保证（§9）。
