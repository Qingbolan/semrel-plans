# 解决的问题

**TAG 模型**（§2，pp.2–3）：给定自然语言请求 R，
1. 查询合成 syn(R) → Q：推断哪些数据相关（如利用 schema），并把请求解析为可执行查询，可以包含 LM UDF；
2. 查询执行 exec(Q) → T：在数据库中高效执行，API 可以支持 LM 算子；
3. 答案生成 gen(R, T) → A：LM 基于 R 与 T 生成答案，可以对数据迭代或递归调用，不必一次把整张表放进上下文。

作者把 TAG 定义为这三步的一次迭代，多跳或智能体循环留作扩展（§2、§5）。Text2SQL（省略 gen）与 RAG（exec 为向量检索、gen 为单次调用）都是特例。

**设计空间**（§3，p.3）：

| 维度 | 选项 |
|---|---|
| 查询类型 | 点查询（一行或几行）与聚合查询（跨多行的总结、排序）；需要数据还是需要推理 |
| 数据模型 | 关系表；也可以是文本、图像、视频、音频，或键值、图、向量、文档存储 |
| 执行引擎与 API | SQL、向量检索、语义算子（如 LOTUS 的 sem_filter）、LM UDF、带 ML 函数的 SQL |
| 生成模式 | 单次调用；或 LOTUS 式的迭代、递归生成 |

阅读者分析：论文提出的是问题定义与基准，并没有给出自动的 syn 实现；§4 中“手写 TAG”由人根据 schema 写管道，因此其成绩不能当作自动规划的成功率（阅读者分析）。
