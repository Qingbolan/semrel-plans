# 贡献与评价

**论文声称的贡献**（§1、§7）：
1. 声明式 YAML 接口与 LLM 专用算子，新增 resolve（实体解析）和 gather（分块时保留上下文）；
2. 13 条面向 LLM 的重写指令；
3. 智能体式的计划重写与评估框架，以及“机会主义”的自顶向下优化策略：只在验证认为需要时才重写；
4. 四个任务上输出比基线准确 21–80%。

**机制要点**：

| 组件 | 细节 |
|---|---|
| 生成 / 验证分工 | 生成智能体按指令改写；验证智能体针对每个算子生成评判提示并在样本上评分（§4.1） |
| 两阶段选择 | 平均评分取前 6，再两两比较；候选可能上百个，全对比较不可行（§4.1） |
| 分块参数搜索 | 分块大小按 LLM token 上限的 15%–75% 和平均文档长度的 15%–100% 采样，并比较多种 gather 背景策略（§4.2） |
| 对比 Cascades | 同为自顶向下，但扩展依据是重写指令，子计划评估靠 LLM 验证（§4.1） |

**阅读者评价**：
- 优点：把“质量不足”而非“代价太高”作为优化对象，针对漏抽、上下文丢失、实体重复等具体失败给出分解方案。
- 优点：§5.5 显式检查智能体实例化指令的可靠性：30 个 LLM 生成的计划中 47% 精确率高于基线、67% 召回率高于基线，但 20% 有严重错误（如提示中漏掉文档占位符）；验证评分与 F1 的 Kendall τ 为 0.642。
- 局限一：评分也来自 LLM，局部“看起来更好”不一定改善全局结果。
- 局限二：样本文档可能都在上下文窗口内，而全量数据中有超长文档，执行时会出错；运行时自适应调整“正在开发”（§4.1）。
- 局限三：优化后成本普遍上升数倍到十几倍（见 benchmark 分析）；作者以 LLM 价格下降为理由，但未做成本约束下的比较。

依据：§1、§4、§5.5、§7、Figure 5，PVLDB pp.3035–3046。
