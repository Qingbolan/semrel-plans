# 解决的问题

**输入**（§2.3，p.4）：用户写的初始流水线 P0（DocETL 的语义算子序列，每个算子含提示模板、输出 schema、模型）；文档数据集，其中 40 篇作为优化样本 D_o；用户定义的评分函数 a(·)（可用标准答案或 LLM-as-judge）；评估预算 B（可执行并打分的候选流水线个数）。

**输出**：在 B 次评估内找到的候选集合上的 Pareto 前沿，即在准确率和成本上都不被其他候选支配的流水线集合（Definition 2.1）。

**成本模型**：LLM 算子成本 = 输入输出 token 数 × 模型单价 × 处理的文档数；代码算子成本记为 0；流水线成本为各算子之和（§2.3）。

**改写与指令**（§2.2、§3）：改写把流水线中一段连续算子替换为新的算子序列。指令（directive）是抽象规则：左边是算子类型模式，右边是新算子序列及其配置如何构造，由 LLM agent 根据任务语义和样本数据实例化。

**搜索方法**（§4）：
1. 把搜索空间看成图，节点是完整流水线，边是一次改写；
2. 用树上 UCB 变体选择下一个要改写的流水线；
3. 奖励不用超体积，而用“边际准确率贡献”（该流水线准确率与同等成本下最佳准确率的垂直距离），并在其后代上聚合；
4. 用渐进加宽限制每个节点的子节点数随访问次数次线性增长，迫使搜索走得更深；
5. agent 先只看指令名称和简介，选中后再加载完整说明（渐进披露），可随时调用 `read_document` 查看样本。

**边界**：目标与评估数据事先给定，是离线的程序优化；改写不保证严格语义等价，质量只在 40 篇样本上估计（阅读者分析）。

依据：[arXiv 2512.02289v4](https://arxiv.org/abs/2512.02289v4)，§2–4、Figure 3，pp.3–9。
