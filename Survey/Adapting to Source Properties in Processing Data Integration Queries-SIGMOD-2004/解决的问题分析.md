# 解决的问题

**输入**：一个已知的 select-project-join-aggregation 查询（不含 SQL 子查询，§4.3），一组只能顺序读取、性质未知且可能变化的远程来源（§3.5）。

**输出**：与单一静态计划相同的完整查询结果，但执行代价更低。

**核心等式**（§2.3，p.3）：并集可分配到选择、投影、连接上。把每个关系切成 n 段后，m 路连接 = 各段同号连接（各阶段计划）∪ 其余所有跨段组合（stitch-up）。跨段组合共有 n^m − n 种（§3.4）。

**机制约束**：
- 每个计划必须缓冲叶子输入，以便后续与其他计划的数据连接（§3.4，p.4）；
- 共享状态结构时，同一时刻只允许一个算子写入并用新元组探测；连接子表达式的元组布局和访问键需兼容，否则要用 tuple adapter、pseudogroup 或重新哈希（§3.1–3.2，p.4）；
- 顺序执行的多个阶段之间不共享结果，只在早期阶段与 stitch-up 之间复用（§3.1）。

**难点**：何时切换、切换到哪个计划。Tukwila 每隔固定时间在后台线程重新优化；未计算子表达式的基数用 System-R 估计与“父表达式可能是主外键连接”两种估计的平均，出现“乘性”连接时把该因子带到后续估计（§4.1–4.2，pp.6–7）。

依据：§2.3、§3.1–3.4、§4.1–4.3，PDF pp.3–7。
