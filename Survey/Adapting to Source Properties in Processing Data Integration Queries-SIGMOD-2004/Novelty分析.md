# 贡献与评价

**论文声称的贡献**（§1，p.1）：
1. 形式化自适应查询处理问题，划分四类互补技术；
2. 提出自适应数据分区框架，相当于自适应处理的“变换规则”；
3. 在 Tukwila（约 8 万行 C++）中实现状态暴露、兼容性处理、执行监控和 stitch-up 计划；
4. 用 ADP 解决三类问题：中途纠正选择率、利用数据顺序、提前聚合。

**机制要点**：

| 组件 | 细节 |
|---|---|
| 状态结构 / 迭代器解耦 | join 与聚合拆成 state structure（list、sorted list、hash、B+ 树等）和 iterator module，使不同计划能共享同一子表达式的状态（§3.1） |
| stitch-up 连接 | 优化器给出已算子表达式的排除列表，按“结构对结构”而非逐元组判断哪些组合需要生成（§3.4.2–3.4.3） |
| 互补连接对 | merge join 与 pipelined hash join 共享 4 个哈希表；按序到达的元组走 merge，乱序的走 hash，可选 1024 元组优先队列重排（§5） |
| 可调窗口预聚合 | 每 w 个元组预聚合一次，有效则扩大窗口，无效则缩小到 1，相当于直通；保持流水线（§6） |

**阅读者评价**：
- 优点：把“正确性”和“复用已做工作”一起处理，不把换计划当作免费操作；同一框架覆盖基数纠错之外的顺序与重复两种性质。
- 局限一：stitch-up 本身有显著代价，作者只称其“常低于总时间的 50%”（§4.4）；阶段越多，跨段组合越多。
- 局限二：基数外推假设查询性能在整个生命周期内一致，作者以“多数连接是主外键连接”为理由（§4.2）；非主外键或强相关数据下的表现未测。
- 局限三：并行计划方案起初把数据碎片化到太多互补计划，大部分计算落到 stitch-up，收益“微薄”，最终改用局部的互补连接对（§5）。
- 局限四：§4.5 显示增量直方图能较早预测连接大小，但给三个来源加直方图使运行时间从 6 秒增到 11 秒，因此 Tukwila 默认不用。

依据：§1、§3.1–3.4、§4.2–4.5、§5–6，PDF pp.1–11。
