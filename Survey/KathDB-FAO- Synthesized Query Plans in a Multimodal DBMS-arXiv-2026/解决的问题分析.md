# 解决的问题分析

来源：[原文](2609.28761v1.pdf)，§2–6。

- **输入**：自然语言查询、DBContext 中注册的关系及文本/图像文件路径，以及可复用函数库。
- **输出**：查询结果及执行它的 FAO DAG；每个 FAO 是输入输出均为关系的生成函数。
- **核心困难**：自然语言没有唯一分解；粗粒度代码缺少中间约束，细粒度算子又可能阻断跨步骤提前终止；候选计划和代码生成本身昂贵。
- **解决路径**：分解原子动作 → 从消费者向生产者传递 schema/取值要求 → 在小样本上执行原子计划以观察中间数据 → 选择动作分组 → 执行时生成融合函数。将有价值的函数参数化保存，并在后续解析阶段用于缩小规划空间。

## 能力边界

1. 主要逻辑重写是固定原子 DAG 上的动作分组，默认组大小上限为 5；逻辑重排留作未来工作（§4）。
2. 原子计划先用真实模型调用做 profiling，每张基表至多抽取 50 行；最优配置 list-rank 用这些观察和原子代码比较候选分组，不执行所有候选融合计划（§4）。不能说它完全不采样。
3. 执行与代码生成交错，可根据已经物化的上游结果写后续函数，运行异常时重新生成代码。这个机制不等于通用的执行时环境探索，也不保证无异常的代码语义正确（§2、§5）。
4. 函数复用保存的是算法和控制流，不是已检索证据或模型结果。复用可提前影响 query sketch，并非只省去最后一次代码生成（§5、§6.5）。

## 证据与口径

评估包含 SemBench 的 Movie、E-Com、MMQA，以及作者新增的十条 Additional 查询；每个查询运行三次。作者报告跨场景相对次优系统平均执行成本降低 58.8%；这是执行成本，不能直接当作包含规划成本的降幅（§6）。

表 2 中 E-Com 的原型质量为 0.77，ClaudeCode+ 为 0.79，执行成本分别为 $0.079 与 $0.176；原型并非始终质量最高。函数复用在两个各十条查询的工作负载上测试，提前参与规划能降低规划成本，但不同查询组成的工作负载几乎没有执行成本收益（§6.5）。

比较限制：BigQuery 数据引用 SemBench，使用不同模型；部分不支持查询被排除，超时查询质量记为 0，多数系统串行执行。应同时读质量、规划成本和执行成本，而不是仅引用最大加速数字（§6.1）。
