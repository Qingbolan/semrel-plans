# 工作负载

**系统与数据**：演示中用户可选择 MySQL、Postgres、Spark SQL 作为目标系统，工作负载来自预定义库中的 Join Order Benchmark（JOB）和 TPC-H，也可注册临时查询（§3，p.3）。摘要只提到 MySQL 与 Postgres，Spark SQL 出现在演示脚本与场景 3 中（摘要 p.1；§3 p.3）。

**场景**（§3，p.3）：

| 场景 | 回退原因 | 期望行为 |
|---|---|---|
| 1a 索引删除 | 一个或多个索引被删除 | 发现最新计划缺少索引扫描，建议重建索引 |
| 1b 新增索引 | 新索引导致基数估计更难、计划改变 | 识别新出现的索引扫描与连接策略变化，建议恢复原计划的配置 |
| 2 调优开关 | 全局开关（如禁用 nested-loop join）有利于部分查询但让其他查询变慢 | 对比计划并推荐修复配置 |
| 3 运行时错误 | 如 Spark SQL 多表连接中间结果膨胀导致 OOM | 将执行日志纳入提示，重新配置 driver 节点参数 |

论文没有给出各场景的查询数量、数据规模、回退因子 φ 的取值或 LLM 型号。

依据：摘要，p.1；§3，PDF p.3（4339）。
