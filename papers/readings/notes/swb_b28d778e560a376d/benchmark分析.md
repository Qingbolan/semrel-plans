# 评测与边界

**设置**（§5.1–5.2，PDF pp.6–7）：统一 gemini-2.5-flash，关闭推理，温度 0（可设时）；LOTUS 1.1.3（e5-base-v2 与 clip-ViT-B-32 嵌入用于连接预筛），Palimpzest 0.8.2（关闭 Abacus 优化器，MaxQuality 目标），ThalamusDB 0.1.15（连接批大小 10），BigQuery（2000 slots，并行度与批大小不可控）；LLM 调用并行度 20；每实验重复 5 次。

**实验 1（各场景，Table 4，PDF pp.9–10）**：

- Movie：在支持全部查询的系统中 BigQuery 各指标最好；Q1、Q5、Q6 因 LIMIT 处理方式不同，系统间成本相差 100 倍以上。
- E-Commerce：只有 LOTUS 和 BigQuery 能完整实现，LOTUS 成本最低且平均质量最好；但其连接阈值靠抽样确定，成本方差最大。
- Wildlife：BigQuery 质量最高但方差大（温度不可控）。
- MMQA：Q7 需 40,000 次 LLM 调用，Palimpzest 超 35 分钟、LOTUS 近 40 分钟。
- Cars：音频过滤普遍表现差。

**实验 2（按算子聚合，Table 5，PDF p.12）**：

| 系统 | 过滤 质量/成本 | 连接 质量/成本 | 平均 质量/延迟/成本 |
|---|---|---|---|
| LOTUS | 0.896 / $0.34 | 0.614 / $2.74 | 0.731 / 212.1s / $0.86 |
| Palimpzest | 0.777 / $0.40 | 0.703 / $3.29 | 0.715 / 165.0s / $1.06 |
| ThalamusDB | 0.698 / $0.19 | 0.487 / $0.14 | 0.592 / 244.2s / $0.17 |
| BigQuery | 0.574 / $0.36 | 0.601 / $1.02 | 0.677 / 31.7s / $0.45 |

表已渲染核对。正文称 BigQuery “平均延迟 48.1s”，对应表中 Avg(Filter+Join) 行（便于与只支持过滤和连接的 ThalamusDB 比较），全算子平均为 31.7s（阅读者分析）。作者声明比较性结论只在均值差至少三个标准差时成立。

**实验 3（扩展性，Figure 1，PDF pp.10–11）**：E-Commerce 与 MMQA 中除 BigQuery 外都无法扩展到大规模，原因是多模态语义连接调用数随表大小平方增长（MMQA Q7 在规模 400 时 160,000 次调用，约 50–60 美元）；数据量增加时质量普遍下降。E-Commerce Q8 内存需求 ThalamusDB 约 250 GB、LOTUS 150 GB、Palimpzest 100 GB；LOTUS 在 Cars 157k 规模可能因调用失败停滞超过 48 小时。

**边界**：所有系统在快速演进，结果为快照；只用一个 LLM；为控制成本只用了小部分数据（§4.6、§6）。阅读者分析：仅一个模型限制了结论对其他模型的推广；不同系统使用各自默认提示，质量差异不完全是执行引擎差异（阅读者分析）。

依据：§5–§6、Tables 4–5、Figure 1，PDF pp.6–12。
