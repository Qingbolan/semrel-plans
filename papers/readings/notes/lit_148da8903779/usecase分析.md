# 具体用例

**PEER 式循环工作流**（Figure 1，§1，p.2；Figure 4，§3.2，p.5）：Planner、Executor、Expresser、Reviewer 四个智能体顺序执行并迭代多轮，每个智能体有很长的固定提示。

**LRU 下的问题**：时刻 13 Executor 在运行，显存不足，LRU 把最久未使用的 Expresser 前缀驱逐；时刻 14 轮到 Expresser，发生缓存缺失，需要重算预填充。

**KVFlow 的处理**：

1. 前端把当前智能体身份和全图各智能体的 steps-to-execution 嵌入 HTTP 请求元数据（§3.3，p.6）。
2. 后端据此更新缓存树优先级：Expresser 距执行仅 1 步，优先级低，不会被驱逐；刚执行完的 Planner 距下次执行较远，其前缀和所有动态后缀优先被驱逐。
3. 如果 Executor 1 的前缀已被卸载到 CPU，则在 Planner 执行期间就开始后台预取；若预取尚未完成，调度器先运行已就绪的 Executor 2 或其他工作流的请求，避免 GPU 空等（Figure 4，pp.5–6）。

**多客户端**：两个应用都定义了名为 Planner 的智能体时，靠客户端 ID 区分，避免互相干扰（§3.3，p.6）。

阅读者分析：该用例依赖工作流拓扑事先已知；语义算子管线（固定的多步 LLM 调用链）也具备此性质，但论文没有在这类负载上评测。
