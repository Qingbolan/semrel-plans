# 出发点

企业数据 80%–90% 为非结构化，应用常需先把文档集合转换为关系表再做 SQL 分析或机器学习（§1，p.1）。现有抽取方法各有长短：OpenIE 抽三元组、PLM 擅长语义理解、LLM 生成代码（Codegen）擅长需要计算的属性（如 Lifespan=卒年−生年），但对“早期写实、后期象征主义”这类语义判断会出错；没有一种方法在所有属性上一致占优（Fig.1，pp.1–2）。LLM 质量最好，但按 token 计费，把每份完整文档都送入 LLM 在大规模集合上代价过高（p.2）。

两个关键观察（p.2）：只送入与属性相关的文本块可以显著降本而质量损失不大；廉价方法在部分情形下与 LLM 一样好甚至更好。难点在于：验证样本少，难以逐文档估计各策略质量；属性值在文档中表述多样，仅用属性名及描述做检索查询信息不足（例如“Genre”的值“Painting”未在句中直接出现）。

阅读者分析：动机直接针对 LOTUS、Palimpzest 这类“整篇文档送 LLM”的语义算子系统的成本问题，把抽取视为成本约束下的计划优化问题。

依据：[PVLDB 18(11)，13 页](https://www.vldb.org/pvldb/vol18/p3695-chai.pdf)，§1，pp.1–3。
