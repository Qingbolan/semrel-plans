# 解决的问题

论文没有给出形式化的问题定义，而是描述系统要完成的转换：把用户的高层分析请求 R 翻译成可执行的工作流 DAG G，并在异构数据源上执行，生成多模态分析产物（§2.2，p.3）。

| 项 | 内容 |
|---|---|
| 输入 | 自然语言请求；用户通过 “@” 显式绑定的数据上下文（如 @Sales Database、@Financial Metrics）；已上传的数据源与知识库文档（§3，p.4） |
| 中间表示 | 规划器输出的逻辑 JSON 计划 → 编译后的 DAG 对象 |
| 输出 | 数据视频、仪表盘、分析报告；可检查的节点内部状态与执行日志 |
| 工作单元 | 节点 N = ⟨D, I, O, C, Φ⟩：语义描述 D、带 ⟨Key, Type, Desc⟩ 模式的输入/输出端口 I/O、配置参数 C、执行逻辑 Φ（§2.1，pp.2–3） |

**两类节点（§2.1，p.3）**：ToolNode 的 Φ 为确定性代码（如 DataConnector、CodeExecutor），幂等、无需推理上下文；AgentNode 是 LLM 驱动的子智能体，可含嵌套子 DAG，使用私有上下文窗口 W_local 与内部工具。**上下文隔离**：全局规划器只看到节点的标准化 I/O 接口，看不到 W_local。

**规划器（§2.2，p.3）**：短期工作记忆（对话历史、中间变量、引擎反馈）+ 长期知识库（向量库：schema 元数据、领域文档、SOP 经验即已验证的历史工作流）。执行前检索 SOP 作为上下文示例；执行失败（如 SQL 语法错误）时把错误轨迹写回工作记忆并重新规划；成功的工作流自动归档，专家在画布上修订的工作流可手动存为 SOP 模板。

阅读者分析：问题边界是“分析工作流编排”，SQL 生成交给作者已有的 DeepEye-SQL（§3，p.4），非结构化文档的处理方式（如何检索、如何与表结果对齐）论文未展开。
