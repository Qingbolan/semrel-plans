# 解决的问题

§2.1 给出两类任务的形式化定义：

| 任务 | 输入 | 输出 | 评测单位 |
|---|---|---|---|
| DE-Arch | 高层业务需求 Q_de + 初始仓库 C0 | 工程规格 S（如数据契约/设计文档） | 单题，非分层 rubric 由 LLM 评审 |
| DE-Impl | 详细规格 S（`data_contract.yaml`）+ 空仓库 | 从零实现的多层 SQL 仓库 C* | DAG 中每个 SQL 节点（表），按 schema+数据精确匹配 |
| DE-Evol | 已有仓库 C0 + 新规格 S | 修改后的仓库 C* | 同上，含 create/edit 节点 |
| DA | 分析就绪数据 D（语义层）+ 开放问题 Q_da | 分析产物 O：报告、关键洞见、建议、图表 | 单题，分层 rubric + GSB |

DE 节点的匹配在 DuckDB 中做"schema+data 精确等价"判定（App. A.1）。DE-Impl 的管线分 staging / intermediate(core) / marts 三层，staging 侧重数据清洗（有效性 48.1%、一致性 22.3%、完整/唯一性 18.9%、异常检测 10.7%，Figure 3）。

DA 题没有唯一标准答案：rubric 把问题分解为需求→子需求→多条可行"路径"，评审为每个子需求选最匹配路径，仅用该路径的条目打分（§2.2、Figure 2）。

阅读者分析：DE 与 DA 目前是分开评测的模块，DA 的输入是现成语义层而不是 agent 自己在 DE 中产出的表；App. F.4 明确把端到端串联列为下一步，而非本文已做内容。
