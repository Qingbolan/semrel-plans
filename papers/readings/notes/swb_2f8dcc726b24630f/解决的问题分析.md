# 解决的问题

**输入**（§3.2、§4.1，PDF pp.4–5）：一条告警调查轨迹（JSON），包含 id、被调查实体（用户、IAM 角色或终端）、账户、租户、时间戳、总体 riskScore，以及 `properties` 中触发的一条或多条行为规则（规则名、描述、证据属性、局部风险分、风险标签）。

**输出**（§4.1，p.5）：符合固定 JSON 模式的分诊报告，包含：

1. 二值判定：可行动（Actionable，需升级为事件）或不可行动；
2. 若不可行动，给出四个子类之一；
3. 以获取到的证据为依据的简短理由；
4. 抽取出的可观测项，如用户、IP、文件、资产。

| 不可行动子类 | 含义（Table 2，p.4） |
|---|---|
| Benign Positive | 可疑但属于预期行为 |
| False Positive—Logic | 检测规则本身有缺陷 |
| False Positive—Data | 数据错误导致 |
| Undetermined | 证据不足 |

**处理单元**：单条告警；每条告警的上下文是临时的，跨告警状态被禁用以防信息泄漏（§4.1，p.6）。

**决策规则**：保守策略，任一工作流判定升级则总体为可行动（§3.1，p.3）。各工作流的判定条件是人工设定的阈值规则，例如云登录风险分大于 1000 且近期有活动（Table 1，p.3）。阅读者分析：因此 LLM 的主要工作是路由、取证和按给定策略填写字段，而非自行学习判定边界（阅读者分析）。
