# 出发点

作者用 Oracle `LOG_FILE_SYNC` 异常说明问题（§1、Figure 1）：资深 DBA 需从 445 个指标中挑出 61 个相关指标，把告警与隐式相关指标（如 `LOG FILE PARALLEL WRITE` 等待时间）联系起来，构造因果链得出"I/O 瓶颈限制 LGWR 写入"的根因。这一过程耗时、难扩展，对重复出现的异常也低效。

现有方法的不足（§1–2、Table 1）：

- **规则方法**（ADDM、DBSherlock、ADTS）：固定阈值、规则有限，易得出误导结论（Figure 1(b) 因阈值把异常归为 redo 激增），且多绑定单一数据库（ADDM 仅支持 Oracle）。
- **机器学习方法**（CauseRank、DBMind、iSQUAD、PinSQL、RCRank）：建立在规则系统上，泛化依赖训练数据，只覆盖特定异常类型。
- **LLM 方法**（D-Bot、Panda、ChatDBA、Andromeda、GaussMaster）：文档切块破坏多步诊断关系，向量相似检索常召回无关知识，检索到的经验碎片化；Figure 1(c) 中 DeepSeek-R1 列出多种可能原因但无法给出具体可执行诊断。

由此提出三项挑战：C1 如何表示和整合碎片化、异构的运维经验；C2 如何捕获未表现出明显异常但与异常隐式相关的指标；C3 如何自适应探索诊断路径并生成可读报告。

依据：[arXiv:2508.01136v1](https://arxiv.org/abs/2508.01136)，§1–2、Figure 1、Table 1，PDF pp.1–3。
