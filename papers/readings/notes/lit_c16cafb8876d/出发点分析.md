# 出发点

旋钮决定内存分配、线程调度、缓存等，例如 MySQL 约有 260 个旋钮；人工由 DBA 试错代价高，云上数万实例时更不可行（§1，PDF p.1）。自动调优系统遵循“试—收集—调整”循环：推荐配置、重放负载得到性能、再调整策略（Figure 1，PDF p.1）。

原文指出现有方法的三点局限（§1，PDF p.2）：

1. 旋钮剪枝与模型初始化依赖历史调优数据或人工收集的文本（Lasso、敏感度分析需大量历史数据，GPTuner、DB-BERT 需手工整理文本，QTune 需历史数据预训练），换新内核或新硬件时要从头收集。
2. 推荐方法每轮都要重放负载，探索/利用能力有限，常需数百轮。
3. 几乎都是黑盒，DBA 难以理解与干预。

已有 LLM 调优工作（如 GPTuner）主要只覆盖剪枝这一子任务，因此作者想系统评估 LLM 在三个子任务上能否像有经验的 DBA 那样工作（§1，PDF p.2）。

阅读者分析：出发点是“LLM 预训练已见过手册与论坛”，所以它衡量的部分是模型对 MySQL 等成熟系统的记忆；作者用 TiDB 作为网上资料较少的引擎来部分检验这一点（§8.1，PDF p.10）。

依据：§1、Figure 1、§8.1，PDF pp.1–2、10。
