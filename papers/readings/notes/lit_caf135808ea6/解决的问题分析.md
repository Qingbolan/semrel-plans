# 解决的问题

**任务定义**：Spider 2.0-Snow 与 Spider 2.0-Lite 是自包含的 Text-to-SQL 任务。输入为数据库模式 D、自然语言问题 Q 和辅助文档 E（外部知识，如 BigQuery UDF 定义），输出一条 SQL S = f(Q, D, E | θ)，以执行结果与标准答案比对。它不同于完整 Spider 2.0 的代码智能体任务（要修改 DBT 等代码库）。

**工作单位**：每个样例一个问题；系统可多次调用 LLM 和数据库（执行 SQL 获取反馈），最终输出一个结果表。

**流水线**：

1. **数据库信息压缩**：P_init = compress(D) + E + Q。按前缀/后缀模式合并相似表，只保留一张代表表的完整 DDL，其余只列表名；压缩后仍超过 50K token 的样例再做表级 LLM 模式链接（逐表问 Y/N 并列出相关列）。
2. **候选生成与自修正**：温度 1.0 生成 k 个候选，每个候选依据执行报错或空结果迭代修正，最多 5 轮。
3. **共识执行**：按执行结果计票；若最高票唯一，则作为高置信答案（X_high）；若出现平票，归入低置信集合 X_low。
4. **列探索**：只对 X_low 触发：LLM 生成至多 10 条带 `LIMIT 20` 的探查 SELECT，由简单到嵌套逐步执行和自修正，再基于探查结果重新生成候选并投票；仍未解决的随机选择（Eq.(7)）。

阅读者分析：“平票”判定只依赖结果相等，问题本身是否有歧义并未被建模；列探索本质上是在执行环境中收集数据画像，用来补足仅凭 DDL 与样本行难以判断的类型和取值。

依据：§3.1、§3.2.1–3.2.3、Eq.(1)–(7)，附录 A、C，PDF pp.3–6、13–14。
