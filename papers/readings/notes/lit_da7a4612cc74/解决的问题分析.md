# problem

**数据模型**（§3.1，PDF pp.3–4，Table 1）：
- 普通表 T_A；
- 文本集合 D：每篇文档由文件路径唯一标识，并假定同一集合中的文档暴露相同的属性；
- latent table D.LT_LA：用户在 D 上注册的 schema，属性在查询执行时才从文本中抽取。

普通表把文件路径存成一列，就相当于对文本集合建立了外键。latent table 分单行和多行两种：多行时，用户必须指定 document-level key，例如球员名。注册 schema、选择表类型、指定键都是一次性工作；后两项可以交给 LLM 自动判断（§3.1；§6.7，p.16）。

**输入/输出**：输入是由传统算子和 MMOps 组成的查询计划，输出是普通表。Table 2（p.4）定义了各算子：
- Scan：把 latent table 物化为 T_{LA∪path}；
- Join：普通表与 latent table 连接；
- Union：普通表与 latent table 合并；
- Projection、Selection、Aggregation：作用于 latent table 或其结果。

MMJoin 的语义定义为"先 Scan，再按 path 做传统 join"（§5，p.9）。

**工作单元**：对每篇文档和每个 latent 属性，模型对文本 token 逐个判断是否构成取值 span（Figure 2 c）。因此取值必须在原文中以字面 span 出现。

**适配新领域**：用户离线标注少量文本中的 span，用于微调（§2.1，p.3）。

阅读者分析：这里的问题是"文本到关系表的按需抽取再做关系运算"，不是自由语义判断或摘要生成。

依据：[arXiv:2410.22522v1，23 页](https://arxiv.org/abs/2410.22522)，§2–§3、§5，Tables 1–2，PDF pp.3–9。
