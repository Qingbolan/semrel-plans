# motivation

语义算子把多模态 LLM 包装成 SQL 算子（如 AI_FILTER），其谓词是自然语言（§1，p.1）。语义数据处理引擎本质上仍是关系系统，仍依赖计划枚举与代价模型，但计划空间更大、还要兼顾近似优化下的准确率。现有系统基本回避基数估计：用固定选择率、简单采样，或把语义算子当作不透明的昂贵算子，只在运行时局部重排过滤（p.1，引 Snowflake AISQL 等）。

作者论证“基数估计更重要而非更不重要”（pp.1–2）：语义算子成本与处理行数成正比，基数估计即成本与延迟预测，估错是“账单意外”；即使总把语义算子放后面，多个语义过滤的相对顺序、代理模型下推的收益、语义连接物理实现的选择仍取决于选择率。

**动机实验**（Figure 1，p.2）：一个三关系语义连接查询（products⋈products、products⋈reviews，各关系 2–3 个语义过滤），枚举 96 个语义等价计划，最便宜 $0.119（524,136 token），最贵 $2.869（13,122,385 token），相差 24.1×；若用固定 20% 连接选择率会选错连接顺序；仅过滤顺序错误也带来 1.43× 成本增加。作者自己承认这是单个查询实例。

**经典方法为何不足**（p.2）：估计本身昂贵（采样需用同一 LLM 评估谓词，成为准确率/成本/延迟三方权衡）；真值依赖模型与提示，没有客观真值；谓词开放且与模态相关，无法预建直方图，唯一可预算的谓词无关信号是嵌入，而嵌入难以表达否定、数量、时间、空间、词汇条件。JOB、STATS-CEB、CardBench 假设客观真值和固定谓词代数；SemBench 关注执行的成本/质量权衡而非基数估计；SemStats、Semantic Histograms 等方法只在各自工作负载上评测，无法横向比较。
