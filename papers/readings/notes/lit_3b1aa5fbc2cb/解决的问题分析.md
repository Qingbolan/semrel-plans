# 解决的问题

**输入**：SQPS 以 UDF 形式注册的语义算子实现，以及一个静态左深查询计划（§4，p.4）。每个算子须声明执行契约的三项属性（Table 1）：

| 算子 | 可流水线 | 谓词（可剪枝） | 笛卡尔积 |
|---|---|---|---|
| sem_filter | Y | Y | N |
| sem_map | Y | N | N |
| sem_join | Y | Y | Y |
| sem_classify | Y | N | N |
| sem_agg | N | N | N |
| sem_topk | N | N | N |

join 实现为 CP + filter；CP 可带 UDF 只返回右表子集，例如用向量索引实现“索引笛卡尔积”（ICP）。CP 的左侧可以流水线，右侧必须是静态输入表（§4，p.4）。

**输出**：查询结果，与请求中心式执行的语义相同；调度被定位为“不改变查询语义或输出准确性”的执行优化（§1，p.1）。

**工作单元**：查询解析器按阻塞算子把计划切成 pipeline，再按 CP 把 pipeline 切成 stage；在一个元组上运行一个 stage 是一个 task，即原子调度单位（§5.1，p.5）。

**核心调度问题**：在 KV cache 容量有界的条件下，对相互依赖（流水线）的算子做在线调度。上游并发过多会在下游复用前驱逐前缀（饱和）；上游并发过少则下游缺少输入、GPU 利用率低（饥饿）。合适的并行度取决于只有执行时才知道的过滤选择率与 join 扇出（§1 p.2；§5.3 pp.5–6）。附加问题：生成长度不定，需要在执行前估计每个任务的 token 上界；显式 pin 内存可能死锁（§6）。

依据：[arXiv 2607.23815v2](https://arxiv.org/abs/2607.23815)，§1、§4–6、Table 1，PDF pp.1–8。
