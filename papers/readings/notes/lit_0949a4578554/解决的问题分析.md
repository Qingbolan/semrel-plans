# 解决的问题

**输入**：OLAP 工作负载 W = {q1,…,qn}（分析型 SQL 查询）、硬件规格 H（CPU 核数、内存）、数据库系统名 D（如 Postgres、MySQL），可选提示 token 预算 B（§2，p.2）。

**输出**：一个完整配置，即一组目标系统可执行的 SQL 命令；对 Postgres 通常是若干 `CREATE INDEX` 与 `ALTER SYSTEM SET 参数 = 值`（§2，p.2）。

**目标**：在 LLM 采样得到的 k 个候选配置中，找出在整个工作负载上执行时间最短的一个，同时控制评测时间、重配置开销与 LLM 调用费用（§2，pp.2–3；§8，p.14）。

**三个子问题**（Algorithm 1，p.3）：

| 子问题 | 形式化 | 位置 |
|---|---|---|
| 提示生成 | 在 token 预算下选择连接条件片段，使所表达连接的总估计代价最大（ILP） | §3，pp.3–4 |
| 配置选择 | 多轮、几何增长超时地评测候选，找出最优配置 | §4，pp.5–6 |
| 配置评测 | 惰性建索引 + 动态规划排序查询，最小化期望建索引代价 | §5，pp.6–9 |

阅读者分析：“最优”只是相对于 LLM 给出的候选集合；如果候选里没有好配置，λ-Tune 不会自己搜索更优解。作者在结论中把这一点表述为假设——从 LLM 输出分布采样“至少能得到一些高效配置”（§8，p.14）。

依据：§2–§5、§8，PDF pp.2–9、14。
