# 出发点

**原文陈述（§1，pp.1–2）。** LOTUS、Palimpzest 等语义算子系统主流采用“解释式执行”：LLM 位于查询执行的内层循环，filter/map 每行一次调用，join 对每个候选对一次调用。每次调用都有延迟、费用与限流开销，调用数随行数（join 随候选对数）增长，在大数据集上代价过高。

作者受 HyPer 把查询计划编译为机器码的传统启发（§2，p.3），主张自然语言语义算子不必总是被当作每次运行时都要重新解释的提示，也可以被当作高层声明式程序，编译成低层可执行代码。

**关键观察（§3，p.3）：** 对很大一类算子，LLM 的逐项行为并非开放式——filter 和 join 输出二值判断，且常基于数据项的隐含属性（例如 “popular courses” 可能隐含按评分阈值判断）。这类算子“表面语义、底层机械”，逐项调用 LLM 等于把同一规则重新推导 N 次。

**更广的主张（§1，p.2）：** LLM 应用不应只优化 LLM 调用的调度、批处理、缓存或剪枝，还应追问何时可以把 LLM 调用从执行中完全移除。

**阅读者分析：** 与 Abacus/Palimpzest 等优化“如何执行 LLM 算子”的工作相比，本文的立场是另开一个物理实现选项；这一点作者在 §2 明确说明是互补关系。
