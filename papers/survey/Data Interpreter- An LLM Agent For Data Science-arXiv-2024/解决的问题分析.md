# 解决的问题

**输入与输出**（§3.1，p.4）：输入是面向任务的需求 x（自然语言项目需求，附数据文件或其他资源）；目标是构造函数 P，使输出 ŷ = P(x) 尽量接近期望结果 y。P 被分解为可直接求解和验证的子过程 p1, p2, …，组成 DAG：ŷ = G({p_i(x)}, R)。

**两层图**（§3.1，pp.4–5）：
- 任务图：LLM 只根据项目需求做规划，不依赖预定义步骤；每个任务节点有描述、类型、状态、执行反馈和依赖；
- 动作图：每个任务拆成若干动作节点，每个动作是一段可执行代码，可同时包含工具调用和 Pandas、NumPy 等普通库逻辑。

**执行与修正**（Algorithm 1，§3.2，pp.5–6）：
1. 按图选出任务节点，检索工具并生成动作图；
2. 执行代码；失败则根据运行时错误让 LLM 调试，最多 M 次；
3. 成功则标为 Success，否则标为 Failure；
4. 失败时基于情景记忆重新生成任务图，拓扑排序后用前缀匹配与原图比较，保留分叉点之前未变化的任务，替换或新增分叉点之后的任务，并直接复用已完成任务的结果。

**工具选择**（§3.3，p.6）：以任务元数据（描述、类型、依赖）为查询，按工具功能 schema 的语义相关性排序，取 top-k；没有合适工具时直接由 LLM 写代码。

阅读者分析：这里的“图优化”是 LLM 重新规划，没有显式代价模型或搜索；top-k 与调试上限 M 是控制参数，不是数据批大小。任务 DAG 是规划结构，若要映射为语义算子，需逐节点核实输入输出与语义，不能把所有 Python 步骤都称为语义算子。

依据：[arXiv 2402.18679v4](https://arxiv.org/abs/2402.18679v4)，§3.1–3.3、Algorithm 1、Figure 3，pp.4–7。
