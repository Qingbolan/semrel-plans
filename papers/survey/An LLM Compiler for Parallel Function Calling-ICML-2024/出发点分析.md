# 出发点

**串行调用的代价**：ReAct 每一步都是“思考→调用一个工具→把观察拼回提示→再思考”。比较两个实体时，第二次查找要等第一次完成；每步都重新调用 LLM，上下文越拼越长，延迟和 token 都随步数增长（§1，pp.1–2，Figure 1）。

**准确率也受影响**：作者观察到 ReAct 有两类常见失败——重复调用同一函数（循环）和在信息不全时过早停止。中间观察拼进提示会干扰后续推理（§1 p.2；附录 A，pp.13–14）。

**已有方案的缺口**（§2，p.3）：

| 方案 | 不足（据原文） |
|---|---|
| Skeleton-of-Thought | 只支持互不依赖的子任务 |
| OpenAI parallel function calling | 仅限 OpenAI 闭源模型；只规划“当前可并行”的一批调用 |
| ReWOO | 规划与执行分离以省 token，但不并行，也不支持动态重规划 |

**核心观察**：许多多工具任务的依赖结构可以在开始时整体写出来，像编译器识别可并行指令一样；即使需要根据中间结果再规划，也可以先并行完成当前已知的独立任务（§1 p.2、§3.4 p.5）。

阅读者分析：本文关心的是单个问题内部工具调用的调度，不涉及跨问题复用已取得的证据或结果缓存。

依据：§1–3，PDF pp.1–5；附录 A，pp.13–14。
