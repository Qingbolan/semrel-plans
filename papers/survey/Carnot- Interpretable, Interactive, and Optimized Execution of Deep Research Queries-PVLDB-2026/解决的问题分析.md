# 解决的问题

**输入**：用户上传的原始数据文件（如 .zip）组织成的命名数据集，可附内容描述；LLM 提供商的 API key；在 chat 中输入的自然语言问题（§2.1，Figure 1）。

**输出**：物理执行 DAG、逐算子结果（含成本标注）、最终答案和可下载的 CSV；以及可编辑的 notebook 工作区（§2.1、Figure 2）。

**前端**（§2.1）：
- 返回计划后先暂停，不花额外 token，让用户在 chat 中审查线性化的计划摘要和 DAG；
- notebook 按拓扑序展开 DAG，每个单元格是一个物理算子，可在三个层次查看：意图的自然语言摘要、生成的代码或 LLM 提示、原始输入输出对；
- 单元格可逐个执行、就地修改（例如改语义过滤谓词，或把 LLM 调用换成确定性 Python 表达式），提交后重新执行该算子并复用未受影响的上游缓存结果；
- 用户可设置成本与延迟预算。

**后端**（§2.2）：Postgres 保存用户、数据集定义和工作区（对话与 notebook）状态；上传文件放在私有 S3；隐私场景可换成本地文件系统和本地模型。

**库**（§2.3）：
- `Dataset` 类封装文件列表，提供可链式调用的语义算子（LLM map、filter、join 等）和 agentic 算子（数据探索、Python 代码生成与执行、通用推理），调用 `Dataset.run()` 才物化；可 JSON 序列化，便于在 notebook 中显示和编辑；
- QueryPlanner 是带 few-shot 示例的 LLM agent，先调用数据发现子 agent 抽样、分析 schema、总结结构，避免过早使用昂贵的 LLM 算子；
- QueryOptimizer 借鉴 Abacus 的 Cascades 式优化器和相似的规则集，区别是由 LLM agent 从估计的成本、延迟、质量 Pareto 前沿中选最终物理计划；
- 另有流式与 notebook 执行层、带缓存的存储引擎和语义索引目录。
