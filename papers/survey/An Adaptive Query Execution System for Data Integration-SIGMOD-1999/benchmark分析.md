# 评测与边界

**实验 1（双流水连接 vs hybrid hash join，§6.2，Figure 3，pp.8–9）**：在 50 MB 数据的全部两表、三表连接上，双流水连接首条元组时间大幅提前，总完成时间也略快，作者归因于多线程可在等待数据时做有用工作。hybrid hash 的表现取决于内外表的指定，双流水连接对此不敏感。初步实验显示给 hybrid hash 加预取几乎能抹平总时间差距，但首条元组优势仍在。广域网下（partsupp ⋈ part），无论哪一侧慢，双流水连接都更早出结果且更快完成。

**实验 2（内存溢出，§6.3，Figure 4，p.9）**：比较 Left Flush、Symmetric Flush 在 32 MB、16 MB 下，以及能装下内存的 64 MB 配置。两者总时间接近；Left Flush 首次溢出后有一段几乎不出元组，Symmetric Flush 出元组更平稳但逐渐变慢。作者结论是应按期望的输出模式选策略。64 MB 只是资源参照，不是等资源基线。

**实验 3（交替规划与执行，§6.4，Figure 5，pp.9–10）**：10 MB 数据上 7 个四表连接，优化器知道来源基数但中间结果基数靠估计。

| 策略 | 说明 | 结果 |
|---|---|---|
| Materialize | 每个连接后物化 | 基线 |
| Materialize and replan | 实际基数与估计相差 ≥2 倍时重规划 | 每个查询都最快 |
| Pipeline | 全流水静态计划 | — |

"物化并重规划"总计比 Pipeline 快 1.42 倍、比 Materialize 快 1.69 倍。作者推测主因是错误估计导致连接分配内存不足而溢出。

**实验 4（保存优化器状态，§6.5，p.10）**：带 usage pointers 的状态复用比从头重规划最多快 1.64 倍；不带 usage pointers 时反而更慢（未给图）。

**边界**：

- 全部基于 TPC-D 合成数据，单一硬件环境，每项取 3 次平均（§6.1）。
- 来源启停的 collector policy 没有单独实验；实证集中在连接和重规划上（阅读者分析）。
- 结果不能推广为"任意来源发现或状态复用都会受益"（阅读者分析）。

依据：[原文](https://www.cis.upenn.edu/~zives/research/adaptive_exec.pdf)，§6.1–6.5、Figures 3–5，pp.8–10。
