# 评测与边界

**被测系统**（§4.1）：Evaporate（先抽表，再执行 SQL）、Palimpzest、LOTUS、DocETL、QUEST（使用作者原代码），以及 ZenDB、UQE（没有公开代码，由作者重新实现部分组件）。统一使用 GPT-4.1-mini。

**抽取查询的准确率**（Figure 2，读图近似值）：
- WikiArt 和 NBA 上，几乎所有系统的 F1 都在 0.85 左右，其中 DocETL 最好，Evaporate 最差；
- Legal、Finance、Healthcare 上，把整篇文档喂给 LLM 的 LOTUS、UQE、Palimpzest 最好，F1 分别约为 0.66、0.52、0.51；
- QUEST 和 ZenDB 只给 LLM 相关的块，因此在多数数据集上较差。例外是 Healthcare：它缺少结构，ZenDB 会退化为读全文（§4.2）。

**过滤查询的准确率**（Figure 3）：先抽属性再判断条件的系统，比让 LLM 直接回答真假的系统（LOTUS）更准。DocETL 依靠多 agent 策略仍然最好；UQE 用回归模型预测剩余文档，因此最差（Summary II）。

Evaporate 的成本记为 “–”，是因为它只用 LLM 分析少量文档来生成抽取代码，不能理解为 0。在短文档的 WikiArt 上，按块抽取会重复处理相同的块，反而比读全文（UQE）更贵（Summary III）；在长文档上，按块检索则更省（Summary IV）。

**逻辑优化**（§4.5，Figures 4–6，各用 5 条查询）：
- 过滤重排（NBA，基于 QUEST）：按 LLM 成本从低到高依次为 (Sel+Cost)/doc、Sel+Cost、Selectivity、Random；
- 过滤下推：Trans-Join（把 join 转成 filter）比传统的 DB-Pushdown 更省；
- join 顺序：Dynamic（ZenDB、QUEST 采用）最省。

**物理优化**（§4.6，Figures 7–11）：
- 模型选择（Palimpzest）：在 WikiArt 上既超过目标准确率又更便宜；在 Legal 上更准，但因为更常调用 GPT-4.1 而更贵（这里的成本是 token 数乘以单价）；
- 模型级联（LOTUS）：在 WikiArt 上省钱；在 Legal 上几乎每个属性都要升级到 GPT-4.1-mini，准确率持平但更贵；
- 并发（Healthcare）：1/2/4/8 线程时延迟依次为 1.46/0.74/0.38/0.20 秒，F1 都是 0.53；
- 聚合：用聚类代替抽取 group-by 属性更省，但相对误差很高；
- join：用 join 键做语义检索可以剪掉文档，但会误删能 join 上的文档。

**消融**（§4.7，Figures 12–14）：
- 嵌入模型越好，QUEST 的效果越好（Qwen > text-embedding-3 > E5）；
- 分块策略中 Semantic 最好，Fixed-length 最差；
- LLM 的排序为 GPT-4.1 > Claude-sonnet-4 > Deepseek-V3 > GPT-4.1-mini > GPT-4.1-nano。

**边界**：
- 只有一个默认 LLM；
- 各系统经过作者适配或重新实现；
- 多数优化实验每组只用 5 条查询；
- 成本以 token 计，不是美元；
- 附录（模板全集、修改清单、提示）不在 v1 中，需要用作者发布的 artifact 补证（阅读者分析）。
