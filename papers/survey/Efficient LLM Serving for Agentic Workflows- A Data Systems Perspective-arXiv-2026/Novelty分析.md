# 贡献与评价

**论文声称的贡献**（§1，p.2）：
1. Helium：把 agentic 工作流建模为以 LLM 为一等算子的查询计划，支持查询内和查询间整体优化；
2. 主动缓存：为静态提示前缀预热 KV 缓存，并维护全局提示缓存以跳过重复算子；
3. 基于代价、缓存感知的调度算法，用模板化基数树刻画提示结构与依赖；
4. 实现与评测：在多种工作流上优于现有系统，且保持精确语义。

**机制要点与相近工作的区别**：

| 对比对象 | 对方做法 | Helium 的差别 |
|---|---|---|
| SGLang（RadixAttention + LSPF） | 请求全部到齐时按最长共享前缀排序 | 在线排序看不到依赖；Helium 在编译期用 TRT 同时建模前缀层次与依赖（§5，Figure 4） |
| Parrot | Semantic Variables 表示单次调用内的提示结构，按缓存前缀路由 | 只有依赖 DAG，没有全局前缀层次，调度是反应式的（§5，p.5） |
| KVFlow | Agent Step Graph 指导驱逐与预取 | 缺少全局计划重写与跨查询调度（§7.2） |
| Palimpzest 等 | 代价模型选算子，常以质量换速度 | Helium 不改变调用对象，结果完全相同（§8） |

**阅读者评价**：
- 新意主要在组合：结果级 CSE/缓存、前缀级 KV 复用、依赖感知调度共同决定执行顺序。消融显示计划剪枝（含 CSE）贡献最大（关闭后慢 23.35%），说明 Trading 工作流中有大量结构重复。
- 调度“接近最优”的证据只来自 7 个缩小实例（2–4 个 agent × 2–4 个查询，单 worker，8192-token KV 上限），不能推广为大规模下的全局最优。
- 相对 vLLM 的 100.92× 来自逐查询顺序执行这一弱基线；与工作流系统 KVFlow 的 1.56× 才是可比的增益。
- 范围限制（§2 Scope、§9）：只支持静态 DAG，条件循环和依赖运行时输出的动态 fan-out 尚未支持；外部 API 调用只按 best-effort 处理；要求同一基础模型。不能据此声称解决了一般动态 agent 工作流。
