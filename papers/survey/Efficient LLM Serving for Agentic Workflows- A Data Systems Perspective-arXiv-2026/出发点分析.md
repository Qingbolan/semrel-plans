# 出发点

**场景变化**：agent 越来越多地以“推测式 / 批量”方式运行——同一工作流模板套在一批输入上，多个 agent 并行或串行探索不同分析，提示和中间结果大量重叠（§1，p.1）。作者把这类负载类比为 LLM 充当算子的批量分析流水线。

**三类差异**（§1 p.2，Figure 1）：

| 差异 | 含义 |
|---|---|
| 算子抽象 | LLM 算子内部按 token 迭代生成，采用连续批处理，不同于 select/filter 的经典批处理 |
| 算子间共享 | LLM 有状态：后续调用延续对话或复用前一个答案，KV 缓存可跨算子复用 |
| 工作流间共享 | 同批查询之间、跨批次（如每日新闻/天气）存在前缀甚至整条子链的重复 |

**现有系统的盲点**（§2，pp.2–3）：
- 推理引擎（vLLM、SGLang）的前缀缓存是被动、按 LRU 驱逐的，看不到 DAG，无法保证相关请求被不相关请求隔开后仍命中（“operator-level myopia”）；
- 编排框架（LangGraph、Spark/Dask UDF）把 LLM 当黑盒，优化器看不到 KV 状态和 prefill/decode 双峰代价；
- 两者合起来：优化器不懂物理执行，执行引擎不懂逻辑计划。

**作者的两点思路**（§2 p.3）：用主动（proactive）缓存替代被动前缀命中；再配一个缓存感知、基于代价的查询优化器来重写计划、安排顺序。

阅读者分析：动机中的 Trading 例子（同一公司基础资料跨天几乎不变）说明，跨批次复用依赖“输入完全相同”，而不是语义近似；这决定了本文结果缓存的适用面（见“解决的问题”）。

依据：[arXiv 2603.16104v1](https://arxiv.org/abs/2603.16104v1)，§1–2、Figure 1、§5 “Proactive Cache Management”，PDF pp.1–5。
