# 解决的问题

**三项扩展**（§1–2，pp.2–4）：

| 扩展 | 内容 |
|---|---|
| Context 抽象 | 继承 Palimpzest 的 Dataset，保留迭代访问；新增用户定义的 `index`（键查找或向量检索）、自定义工具和自然语言描述 `desc` |
| compute / search 算子 | 都以 Context 为输入、物理实现为 SmolAgents CodeAgent；compute 生成指定输出，search 找信息来充实 Context 描述；智能体带有"用优化过的语义算子程序执行自然语言指令"的工具 |
| ContextManager | 每次 compute/search 产生一个新 Context（类似物化视图），对其描述做嵌入并缓存，供后续相似指令检索复用 |

**设计理由**：同时暴露迭代和索引访问，智能体就能按查询决定先做嵌入检索还是遍历全集；描述字段帮助判断哪些文件可能有用（§2.2，p.3）。

**优化：已实现与未实现**（§3，p.4）：

| 类别 | 内容 | 状态 |
|---|---|---|
| 逻辑 | 用 LLM judge 拆分欠明确或过复杂的指令；合并相似的 search/compute；compute 反复失败时运行时插入 search | 全部为未来工作 |
| 物理 | 让优化器为智能体选模型（类似 Abacus） | 设想 |
| 物理 | 复用缓存的 Context 增强或替代 compute 的输入 | 已实现初步版本，仍属实验性 |

阅读者分析：实验中的优化实际发生在智能体所写的 Palimpzest 子程序内部（如过滤后不再处理、选更便宜的模型）；对高层 compute/search 算子本身的代价与质量建模，论文没有给出（阅读者分析）。

依据：[原文](https://www.vldb.org/cidrdb/papers/2026/p30-russo.pdf)，§1–3、Figure 2，pp.2–4。
