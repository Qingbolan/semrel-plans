# 出发点

**真实数据交互不是一次成型的查询**（§1，pp.1–2）：用户请求常含糊（如 Figure 1 的“需要紧急养护的文物”），系统要先澄清；初版 SQL 可能执行失败，需要按报错修改；用户确认后还会基于中间结果追问。评测实用性需要覆盖完整的交互过程。

**现有多轮基准的两个缺陷**（§1，p.2）：

| 缺陷 | 具体表现 |
|---|---|
| 对话历史是静态的 | CoSQL、Learn-to-Clarify 等给所有模型同一段干净的历史，不记录失败尝试与澄清，无法奖励好的交互策略，也无法惩罚把对话带偏 |
| 任务只读 | 只覆盖 BI 式 SELECT，忽略 INSERT/UPDATE/DELETE、ALTER TABLE 与事务控制等数据管理操作 |

**用户模拟器的问题**（§3.3，p.5）：用 LLM 模拟用户可规模化评测，但常见模拟器会泄漏 gold SQL 的信息，或偏离原始任务需求。

阅读者分析：这篇论文提供的是评测环境，而非新的查询系统；它把“系统在运行中通过提问或查知识库获取缺失信息”变成可测量的指标（阅读者分析）。

依据：§1、§3.3，PDF pp.1–5。
