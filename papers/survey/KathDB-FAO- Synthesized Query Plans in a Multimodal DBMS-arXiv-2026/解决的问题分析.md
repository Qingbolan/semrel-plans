# 解决的问题

**输入**：自然语言查询；DBContext 中注册的关系及文本、图像文件路径；可复用的函数库（§2，p.3）。

**输出**：查询结果，以及执行它的 FAO DAG。每个 FAO 是输入输出均为关系的函数，函数体在查询执行时由 LLM 合成（§2–3，Figure 3）。

**核心困难**：自然语言没有唯一分解；粗粒度代码缺少中间约束，细粒度算子又会阻断跨步骤提前终止；候选计划与代码生成本身也昂贵（§1）。

**解决路径**（§3–5）：
1. Parser 把查询拆成语义原子动作，组成 query sketch，并标注关系型/语义型动作（Figure 4）；
2. 在每张基表至多 50 行的均匀样本上用真实模型调用执行原子计划，物化中间关系并记录代价（§4）；
3. 从消费者向生产者自顶向下传播对 schema 与取值的要求，形成相邻 FAO 之间的契约（Figure 6）；
4. 枚举动作分组（每组最多 K = 5 个动作，只对语义动作分组），用 list-rank 让 LLM 对候选计划做相对排序，选出最便宜的；
5. 执行时为获胜计划的每个融合组生成代码；运行异常时重新生成；
6. 由 LLM 判断哪些函数值得参数化保存（llm-judge），后续查询在解析阶段即可匹配复用（reuse-before）。

**能力边界**：
- 只在固定原子 DAG 上做动作分组；算子或 join 重排等逻辑重排留作未来工作（§3，p.5）。
- 有采样：原子计划在样本上执行，但 list-rank 不执行各候选融合计划，而是看原子代码与样本统计来比较（§4）。不能说它“完全不采样”。
- 执行与代码生成交错，可依据已物化的上游结果写后续函数；这不等于通用的执行时环境探索，也不保证不报错的代码语义正确（§2、§5，阅读者分析）。
- 复用保存的是算法与控制流，不是检索到的证据或模型结果；复用可影响 query sketch，而不只省去最后一次代码生成（§5、§6.5）。

依据：[arXiv 2609.28761v1](https://arxiv.org/abs/2609.28761v1)，§2–5、Figures 3–6，pp.3–8。
