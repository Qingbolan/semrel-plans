# 出发点

**场景**（§1，p.1）：UQE、ZenDB、LOTUS、Palimpzest 等系统让用户选一批文档、指定可从中抽取的属性，再做过滤、聚合、连接。例如律师要找“谋杀、至少三项指控、刑期 15 年”的案件，或分析 NBA 球员与球队信息。这些属性还不是结构化列，主要成本是用 LLM 从每篇文档抽取属性，而不是执行 SQL 比较。

**优化目标**（§1，p.1）：最小化抽取的 LLM 代价，拆成两部分：(1) 降低每次抽取的输入 token；(2) 减少抽取的次数。

**现有做法的不足**（§1、§6，pp.1–2、12）：
- 先抽取全部属性再交给关系优化器，会抽取大量最终用不到的值；
- 关系数据库按选择率给一个查询定一个统一过滤顺序，但同一属性在不同文档中相关片段的长度差别很大，统一顺序会浪费 token；
- 普通 RAG 只用属性名和描述做检索，常漏掉不含字面属性词的片段（例如用出生日期表达年龄）；ZenDB 只在片段级过滤，可能把其他主题文档中的片段误判为相关。

**因此**：QUEST 采用“执行时优化”，逐文档用实际检索到的片段 token 数估计代价，并在前置过滤失败时停止后续抽取（§2.2，p.2）。

依据：[arXiv 2507.06515v2](https://arxiv.org/abs/2507.06515v2)，§1–2、§6，PDF pp.1–3、12。
