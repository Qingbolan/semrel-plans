# 解决的问题

**输入**：一个 Android 应用的源码快照，以及按固定顺序排列的一批数据流分析任务。每个任务包含一个源点（具体到文件、行、语句与源点类别）和六类目标 sink（log、network、icc、file、database、storage）（§5.1，pp.10–11）。

**输出**：每个任务的数据流分析报告；中间产物是应用内共享的知识库。

**目标**：在保持分析质量的前提下，降低整批任务的端到端 API 费用（含知识管理费用）。

**三阶段复用循环**（§3–4，pp.5–9）：

| 模块 | 做法 |
|---|---|
| M1 选择性知识提炼（§4.1） | 任务完成后向同一 agent 追加提炼请求，只能使用已读过的代码证据、禁止新的搜索；候选须满足有证据、有边界、可操作三条规则，按六字段模板填写（摘要、适用条件、回退措施、可跳过内容、优先检查、代码证据）；比较当前结果与历史结果的方法调用链，用重复出现的子路径界定候选范围 |
| M2 打包与准入（§4.2） | 附上匹配规则（exact_symbol、call、symbol_tail、package_prefix 四类，组织为 require_any / require_all / exclude）和下游代码提示（如参数值到下一个处理器位置的映射）；确定性检查必需字段与锚点是否可匹配、是否足够具体，锚点不足时有限次修复，仍不通过则丢弃 |
| M3 上下文感知的运行时注入（§4.3） | 在任务提交时和每次工具调用返回后，对新暴露的文本（context delta）先查 exclude、再查正向规则；按匹配得分排序，在字符预算内注入紧凑块，已注入过的条目只给简短提示，只附与当前上下文匹配的下游提示；OpenCode 实现中经用户输入通道插入 |

**边界**：共享代码的知识可以复用，但不同源点的泄漏结论不同，任务特定的下游检查仍需完成（§2.1）。只研究固定代码快照，跨版本的知识失效不在范围内（§6，p.18）。

依据：[arXiv 2607.11308v2](https://arxiv.org/abs/2607.11308)，§2–4、§5.1、§6、Tables 1–2、Figures 3–7，PDF pp.3–11、17–18。
