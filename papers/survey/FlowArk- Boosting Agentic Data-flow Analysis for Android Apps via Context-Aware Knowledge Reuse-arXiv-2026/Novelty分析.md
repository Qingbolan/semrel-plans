# 贡献与评价

**论文声称的贡献**（§1，p.3）：
1. 刻画批量 agent 数据流分析中的重复分析瓶颈：上下文隔离的实例反复分析共享代码，累积不必要的 token/API 费用；
2. 提出 FlowArk：从完成的分析中提炼可复用知识，打包为可匹配条目，并注入活跃 agent 的上下文；
3. 在真实 Android 应用上评测，费用节省在不同 LLM 和重复运行中一致，分析质量相当。

**优点**（阅读者分析）：
- 复用对象和触发时机都由真实代码路径汇合来解释，直接支撑“执行后才出现共享机会”的动机（§2）。
- 把知识管理费用计入总费用（Main49 上 $43.66），没有只报告分析侧省下的部分（§5.2）。
- 无关知识替换实验把同样长度的其他应用知识注入同样位置：分析费用的降幅从 48.25% 跌到 7.04%，说明收益来自知识内容，而不是额外提示本身（Table 8）。
- 消融中去掉运行时注入（只在任务开始时注入）费用上升 27.97%，是三个模块中最大的，直接支持“时机”这一论点（Table 9）。

**弱点**（阅读者分析）：
- 质量审计基于 257 个抽样任务和“各系统报告结果的并集”，只能给出相对召回，不能给出真实泄漏的绝对召回（§5.4）。
- 相对 F1 上 FlowArk（49.88%）略低于 Mem0（50.80%）和 RAG（51.65%）；“质量相当”成立，但不是更好（Table 7）。
- 没有报告墙钟时间（作者解释为 LLM 服务负载波动），本地嵌入计算未计价；费用下降不能直接推出整批更快完成（§5.1）。
- Main49 选的是源点最多的 50 个应用，有利于出现重叠；知识依赖固定代码快照，长期运行中的失效与净收益未验证（§5.1、§6）。

**与本项目的关系**（阅读者分析）：这是“跨 agent 实例的运行时知识复用”的直接近邻，本项目不能把“发现重叠后共享分析”本身当作新意。

依据：[arXiv 2607.11308v2](https://arxiv.org/abs/2607.11308)，§1–2、§5.1–5.5、§6、Tables 7–9，PDF pp.1–4、10–18。
