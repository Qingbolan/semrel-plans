# 解决的问题

**设想的输入与输出**（§3.1，Figure 2）：输入是用户用多模态算子写的声明式程序（Python API），以及一个由多个底层存储（如 PostgreSQL 存表、MongoDB 存文本）组成的数据湖；输出是跨来源执行并汇总后的答案。

**系统组件**（§3.1）：

| 组件 | 职责 |
|---|---|
| 声明式查询接口 | 以表为初始数据模型（属性可为结构化值或自由文本），提供多模态算子作为程序原语 |
| 数据发现 | 程序未指明来源/模态时，建立跨源语义映射，检索相关来源 |
| 查询规划与优化 | 逻辑计划描述算子依赖；物理计划把程序改写成各系统的查询语言（SQL、Cypher、LLM 提示）；决定执行顺序 |
| Verifier | 计划有多个根时汇总结果：规则过滤合并、把结果放进提示让 LLM 生成，或人参与 |

**多模态算子**（§3.2）：Selection、Projection、Join、Aggregation、LookUp（关键词检索、相似度检索、LLM 推理）、Ranking、Conjunction（并、交、差），另可继承 Operator 基类定义 UDO（如图上的路径查询）。与 LOTUS 的区别：算子定义与实现方式（关系或语义）无关；谓词可写成 JSON 等半结构化形式，而非只用自然语言。

**逻辑计划**：一片森林，每棵树的根是子计划输出，Verifier 作用于所有根之上（§3.2）。

阅读者分析：以上均为设计提议；论文没有给出发现模块、优化器或 Verifier 的实现与评测，§5 只评测了两个独立基准（阅读者分析）。
