# 出发点

**真实场景**（Example 1.1，§1，p.1）：加州某市公设辩护人办公室想检查“加重情节”（持枪威胁、致重伤、绑架等）是否在不同族裔间被公平适用。他们需要从数万页警方报告和庭审记录中抽取加重情节及证据，初始流水线通常只有一个 map：“列出八类加重情节中出现的每一项及其证据”。

**准确率与成本都要管**（§1）：传统优化器只最小化成本；这里若准确率太低（例如低于辩护人要求的 95% 精度），输出就没有用。优化器应给出一组跨不同成本的高准确率计划，让用户按预算选择。

**最优子结构不成立**（§1，p.2）：Cascades 等搜索依赖“最优计划由最优子计划组成”。但在 LLM 流水线中，若把单个 map 拆成“每类情节一个 map + 一个 reduce”，抽取更少文本的 map 单独看更准，带更多上下文的 map 却可能让下游 reduce 更好地去重和过滤误报。哪个 map 最好取决于后面的 reduce。

**已有优化器的局限**（Table 1，§1，p.2）：

| 优化器 | 目标 | 局限 |
|---|---|---|
| LOTUS | 只降成本 | 要求用户先写出准确的计划；每个算子只考虑一种优化实现 |
| Abacus | 准确率与成本 | 用 Cascades 搜索，依赖最优子结构 |
| DocETL-V1 | 只优化准确率 | 自上游向下游逐个优化，错过依赖下游的改写 |

阅读者分析：这反驳了“语义系统只能执行预定算子”的过强说法；但程序改写优化与运行时环境发现是两回事，仍需区分。

依据：[arXiv 2512.02289v4](https://arxiv.org/abs/2512.02289v4)，§1、Example 1.1、Table 1，pp.1–3。
